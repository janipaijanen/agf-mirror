## One gap: gate-self-test coverage didn't grow with the new gates

`always/gate-self-test-rule.md` (MUST-strength in this project)
requires a negative test for every gate a change introduces — "skipping
it for small gates" is explicitly forbidden by that rule's own text.
This revision added three new gates (Maintainer-only access level,
protected-tag existence, post-merge ref-retention API proof), all
correctly specified in the plan's contract sections. But the "Gate-
self-test evidence" section (micro-task 6 / validation section) still
lists only the original three negative scenarios: no binding Governor
decision, target not protected/wrong SHA, functional file in the diff.
None of the three newly-added gates has its own negative scenario.

Concretely missing, per `gate-self-test-rule.md`'s own bar:

- A scenario where the target/source branch access level is 30
  (Developer) instead of 40 — expected result: `STOP`, not silently
  proceed.
- A scenario where the intended stable tag has no matching
  protected-tag rule at tag-creation time — expected result: `STOP`.
- A scenario where the post-merge API check shows one of the two
  maintenance refs missing (the exact failure mode `e2tk` found live
  on MR !1289 today) — expected result: escalate, not silently
  continue to tag/publish.

This doesn't undermine the plan's design, which is sound. It's a
completeness gap against this project's own MUST-strength rule for
introducing gates, and it's the kind of thing worth closing before
Gate 1 rather than discovering during implementation's own Gate 2 self-
test writing.
