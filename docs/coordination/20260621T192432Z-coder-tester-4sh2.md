# Handoff: first-time docs and session-continuity critique

The governor-reviewer asked for a critical but empathetic review of what a
first-time human expects to find from the documentation and README, with special
attention to `/compact-agf` as a useful save-state mechanism before compact,
reboot, plugin restart, or cold-start recovery.

Two advisory reviews were run:

- first-time human evaluator/adopter review of README and public docs nav;
- human/AI operator review of `/compact-agf`, session resume, and durable
  closeout guidance.

The conclusion is not just "add a page." The documentation architecture needs a
defensible answer to this question:

> Does AGF want first-time humans to discover trust, objections, and operational
> continuity from top-level docs, or only after they already understand AGF's
> internal vocabulary?

## Findings that need planner-architect judgment

### 1. FAQ is probably a top-level trust node, not a hidden subsection

Current site nav has `Home`, `Use cases`, `Documentation`, `Reference`, and
`Evolution`. A first-time evaluator looking for objections has no obvious
`FAQ` or `Questions` entry.

The answers exist, but they are scattered:

- `agf/docs/site/index.md` explains what AGF is and is not.
- `agf/docs/site/use-cases.md` covers some non-use cases.
- adoption pages cover cost and exit.
- `agf/docs/site/docs/start/should-you-adopt.md` is a decision page, not a
  quick objections index.

Challenge: either justify why `Should you adopt?` is the FAQ-equivalent entry,
or promote FAQ to a top-level nav peer. My bias: add top-level `FAQ` because AGF
asks for trust before install.

Expected first-time questions include:

- Is AGF a service, runtime, prompt pack, CI tool, or governance framework?
- Does it work with one AI assistant, or only a panel of agents?
- What does it cost per change?
- What happens when a gate blocks work?
- Can I stop using it without rewriting project history?
- What do humans still decide?
- Where do I download the optional Rust `agov` tooling?
- How do I continue safely after compact/reboot/restart?

### 2. README is clear, but it sends humans into source paths first

`README.md` links the published docs, then its five-minute path points into
`agf/docs/site/...` source files. That is helpful for contributors in a checkout,
but a public evaluator expects polished Pages URLs first.

Challenge: justify source-file links as the primary README path, or make the
README human-first:

- browse the published docs first;
- use source links only when reading from a checkout;
- distinguish evaluation, trial adoption, and tooling installation.

Concrete expectation: a first-time human should quickly understand whether to
clone the repo, download a release archive, copy only `agf/`, or install `agov`.

### 3. The Start/Adopt boundary is muddier than it looks

`Your first governed change` is under the `Adopt` nav group but physically lives
under `docs/start/first-governed-change.md`. This is not technically broken, but
it weakens the mental model: "Start" means decide; the first governed change is
the first trial/adoption action.

Challenge: decide whether to move the page under `docs/adopt/`, or redefine
`Start` as "decide and first run." The current split requires a newcomer to
learn the content model by inference.

### 4. Quick reference is hidden and may be mislinked

`agf/docs/site/docs/index.md` references Quick reference but links to a broad
external GitLab URL. The repo has `agf/docs/reference/quick-reference.md`, but it
is not visible in the public site nav.

Challenge: decide whether Quick reference should be a top-level Reference item
and whether the docs index should link to the shipped local page rather than an
external repo landing page.

### 5. Session continuity is operationally valuable but not discoverable

The user specifically identified `/compact-agf` as useful because it saves
current state before compact/reboot/plugin restart, and `agf session resume` can
then reload enough context for a human or AI to continue.

That save/load loop is a strong AGF pattern:

1. before context loss, write durable state to coordination;
2. after restart, run session resume;
3. read must-read files;
4. continue from files rather than session memory.

But the current docs make it hard to discover:

- public docs `Operate` nav has day-to-day operation and review/release only;
- `docs/reference/session-resume.md` is practical, but outside the public docs
  nav and linked mainly from `AGENTS.md`;
- `/compact-agf` appears to live in a worktree draft, not the active branch;
- the closeout shape exists in proposals and command drafts, but not as an
  obvious convention/rule/site page.

Challenge: choose one architecture and defend it:

- public Operate page: `Session continuity`;
- project-local operator documentation only;
- coordination README convention;
- formal rule for required closeout before compact/handoff;
- tool-specific `/compact-agf` command as a convenience over a more general AGF
  closeout convention.

My bias: put a short public `Session continuity` page under Operate, with
`/compact-agf` described as a tool-specific convenience, not as the AGF contract.
The contract should be "durable closeout note plus session resume."

### 6. Command surface and branch examples need cleanup before promotion

The session-continuity docs currently mix command surfaces:

- `docs/reference/session-resume.md` says session resume is Mix-only;
- `/compact-agf` draft appears to lead with `agov session resume`;
- current root `./tooling/agov` does not expose `session resume`;
- examples alternate between `master` and `main`;
- `docs/reference/session-resume.md` still says the manifest default is
  `../../agents-govern/agents/MANIFEST.yaml`, while active authority is
  `agf/agents/MANIFEST.yaml`.

Challenge: before any public promotion, decide which command surface is current
and write examples that cannot mislead a cold-starting human or AI. If Rust
`agov session resume` is planned but not shipped, say so plainly.

### 7. Claims need evidence or softer wording

Session-continuity proposal material includes token ROI and "payback first day"
claims. They may be true in foundry use, but before promotion they need either:

- telemetry citation;
- "foundry estimate" framing;
- softer wording.

Challenge: identify which numbers are measured and which are estimates before
placing them in public docs.

## Requested planner-architect response

Please answer with a coordination note or plan that explicitly addresses:

1. Should FAQ be a top-level docs node? If not, what page carries that job?
2. Should README prefer published docs links over source-doc links?
3. Should Quick reference be visible in the site nav?
4. Where does session continuity belong: public Operate docs, project-local
   operator docs, a rule, or coordination convention?
5. Is `/compact-agf` a foundry-local Claude command, an adopter-facing pattern,
   or both?
6. Should compact closeout use plain `kind: note`, or should active-work saves
   have a machine-detectable topic/schema convention?
7. What must be fixed before this can be presented to first-time humans without
   expert oral tradition?

Be willing to argue against this critique, but please justify the architecture.
If the current shape is intentional, name the user journey it optimizes for. If
not, propose a small release-prep docs slice with review focus.
