# Revise !2373 for split ordinary/DinD runner routing

The release-critical runner state changed after the independent CLEAR on
!2373. Project runner `55975189` (description `dind`) is now registered,
online, active, unpaused, and idle. The governor states that it carries the
`dind` tag. Project-level API access does not expose its detailed tag list, so
the tag statement remains governor-supplied configuration evidence until a
tagged job selects it.

Pipeline `2823154949` proves why a split is needed. Mandatory native-musl
packaging succeeded on the ordinary runner, while `agov:oci:mr-build-scan`
(job `16326536339`) built the image but could not run nested Trivy because
mounting `/proc` was denied. `rust:tooling:oci-pull-test` (job `16326536352`)
then failed during executor preparation after the ordinary runner's rootless
Podman socket disappeared. Neither failed job should be retried unchanged.

The current !2373 plan only accompanies !2362's global default tags and says
no further `.gitlab-ci.yml` edit is needed. That is no longer a sufficient or
accurate design. Please revise it before Gate 1 to specify:

1. ordinary jobs, including mandatory native-musl Linux preview/release
   packaging, remain on the ordinary private runner;
2. jobs that actually execute or depend on nested container workloads receive
   `tags: [dind]`: at minimum `agov:oci:mr-build-scan`,
   `rust:tooling:oci-pull-test`, `agov:oci:release`, `release:verify`,
   `rust:tooling:preview:windows-package`, and
   `rust:tooling:build:windows:preview`;
3. acceptance includes a tagged runner-selection proof plus successful nested
   build/run or pull evidence, not merely API-reported runner availability;
4. the two gate-accompaniment tests assert the live split-routing invariant,
   with deliberate RED-then-GREEN proof;
5. implementation is sequenced ahead of !2392 and then !2392 is rebased, to
   avoid the already-reported collision in both Rust test files.

This is release-priority work. The agentic-work-order assessment requested in
`htar` is acknowledged as a valid later obligation, but it must not displace
the runner-routing correction while the v2.9.0 release lane is blocked.
