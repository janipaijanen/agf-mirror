Recommendation: **CLEAR the learning and accept the factual gap. Do not turn

Authority: advisory review only. This is not Gate 1 and does not authorize

## Independent factual check

- The cited frozen DD report states 0 of 4,180 commits and 0 of 39 tags were
  signed at its assessment revision. Current `origin/main` has advanced, but
  `git log --format=%G?` and `git verify-tag` still find zero verified commits
  and zero verified tags across the checked repository history.
- The ten most recent GitLab Releases expose archives, checksums, and custom

- The adopter release-artifact page explicitly says release signing and SBOM

The learning correctly labels this as a verified capability/procurement gap,
not evidence that a compromise occurred. Its `minor` project-learning severity
is defensible for a single-maintainer, pre-customer project even though an
enterprise assessor may rate the resulting procurement risk High.

## Recommended decomposition

### Slice A — release-bound SBOM, independent of signing

SBOM generation has immediate inventory and vulnerability-management value
without a signing identity, so it should not wait for the harder trust decision.
First run a bounded tool comparison on the exact release products:

1. `cargo-cyclonedx` for the Rust workspace/binary dependency graph at the
   actual target and feature set;
2. Syft against the packaged archive and OCI image for deployed/package and
   OS-layer coverage.

Select the smallest combination that covers the actual release units rather
than choosing a tool by brand. Acceptance evidence should include schema-valid
CycloneDX JSON, deterministic association with the exact release commit and
artifact digest, no dev-only dependency inflation, OCI OS-package coverage,
and a negative test proving release creation fails before publication when a
mandatory SBOM is absent or mismatched. Publish the SBOM beside each relevant
release asset; do not claim one workspace dependency list describes the source
archive, static binary, and container equally.

Tool-capability basis (primary sources, checked 2026-08-17):
`https://github.com/anchore/syft` documents archive, filesystem, container,
CycloneDX, and SPDX support; `https://docs.rs/crate/cargo-cyclonedx/latest`
documents feature/target-aware Rust dependency SBOM generation.

### Slice B — signing identity proof-of-concept, then policy choice

Prioritize authenticity of immutable release artifacts, OCI digests, SBOMs,
and annotated release tags. Requiring every development commit to be signed is
lower value and should not be the first milestone.

Preferred experiment: CI-bound keyless Cosign signing using a narrowly scoped
GitLab OIDC ID token, a protected release/tag pipeline, identity-policy checks
for issuer/project/ref claims, and retained Sigstore bundles/transparency-log
evidence. This avoids a long-lived private key but still depends on forge and
public-root availability and requires precise verifier instructions.

Fallback experiment: maintainer-controlled, hardware-backed signing key with
offline recovery/revocation procedure. Do not place an exportable private key
in ordinary CI variables merely to make the pipeline green; that recreates a
single secret compromise path and key-loss continuity problem.

The proof-of-concept must demonstrate verification from a clean adopter
environment before a mechanism is selected. A GitLab OIDC token by itself is
not the product policy: protected-ref constraints, exact expected identity,
artifact digest binding, tool pinning, revocation/continuity, and verification
instructions are part of the decision.

Identity-mechanism basis (primary sources, checked 2026-08-17): GitLab's
`https://docs.gitlab.com/ci/secrets/id_token_authentication/` documents
short-lived CI OIDC tokens and stable project/ref claims; Sigstore's
`https://docs.sigstore.dev/cosign/signing/overview/` and
`https://docs.sigstore.dev/cosign/signing/signing_with_blobs/` document
identity-bound ephemeral certificates, transparency evidence, and verifiable
bundles for files. Compatibility and exact claim binding still require the
proposed project-specific proof-of-concept.

## Sequencing recommendation

1. Finish the already-active !1712 Gate 1 recovery decisions/corrections; it
   is a current legal/business publication blocker.
2. Correct and decide the R8 Phase-0 baseline plan, but do not start its new
   tooling under the current mismatched plan.
3. Plan and implement the independent SBOM slice before signing. It is bounded,
   externally useful, and does not require a trust-identity decision.
4. Run the signing proof-of-concept, then bring the evidence and identity/
   custody trade-off to the governor for its own Gate 1 decision.
5. Add adopter verification instructions and negative gate tests to whichever
   mechanism is selected; only then call signed/SBOM-bearing releases a
   deployable capability.

Parallel research by build-engineer is reasonable, but it must not mutate CI,
keys, protected tags, or release state before the applicable plan and security
consultation are approved.

## Required consultations for later plans

- build-engineer: release-stage integration, artifact graph, and paid-CI cost;
- infosec-sentinel/human security review: OIDC claims, key custody, protected
  refs, secret handling, trust roots, revocation, and threat model;
- contribution-auditor: scope and claim-strength review;
- governor-reviewer: all Gate 1/Gate 2 decisions and any key/tag/release action.

This disposition accepts the learning while deliberately parking mechanism
selection until the two bounded discovery slices produce evidence.
