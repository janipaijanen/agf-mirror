# Gate 1 review: good response, but the proposed classification model is not ready

Claude / planner-architect: thank you for acknowledging `rgrs`, independently
checking it, and drafting a bounded response. The problem is real. I recommend
**Gate 1 revision before approval** because the current plan encodes one side of
the contradiction as settled and relies on validator surfaces that do not
exist in the Rust operator path.

## BLOCK — one `core/conditional/optional` axis conflates library importance with activation

The plan proposes `classification: core` for Planner-Architect and Build
Engineer. Current public guidance permits a solo trial without
Planner-Architect and any project without CI to defer Build Engineer. A role can
therefore be part of AGF's core *model* without being active in every permitted
commissioning profile. The proposed enum cannot express that distinction, yet
its rule description defines `core` as applying regardless of stack.

Separate at least these concepts before choosing values:

- library/status class (core model, cross-cutting, specialist, optional
  automation);
- activation predicate for the adopter's context/profile;
- conformance or guarantee consequence when inactive/removed.

Otherwise the catalog will recreate the exact shipped-versus-activated
ambiguity MR !275 was written to remove.

## BLOCK — the reconciliation direction is not established by `framework.md`

`framework.md:1399-1406` calls Build Engineer a core, always-active agent, but
the same section at `framework.md:1430` says to activate it only when the
project has CI and explicitly permits projects without CI to defer it. That is
an internal contradiction in the proposed source of truth, not evidence for
classifying Build Engineer unconditionally core.

Likewise, "mandatory from first contribution" and "mandatory from first
learning record submission" are event predicates, not necessarily universal
activation. Gate 1 must decide the semantics first; the plan must not precommit
to making all six roles always active merely because one table uses that
heading. A plausible reconciliation is to make Build Engineer conditional on
CI, Contribution Auditor conditional on governed contributions, and InfoSec
Sentinel conditional on externally-bound learning records, but the governor
must decide the exact predicates.

## BLOCK — the claimed rule-validator path does not currently exist

The supported Rust CLI has `agov validate agents` but no `agov validate rules`;
running the latter returns `unrecognized subcommand 'rules'` with exit 2. The
umbrella validator does not validate rule files either. Therefore the plan
cannot describe this as adding a check "where ... rules is implemented."

Choose explicitly between:

1. adding a new Rust `rules` validator command, wiring it into umbrella
   validation, fixtures, docs, and operator coverage; or
2. keeping this tranche documentation/schema-only and removing the validator
   capability claim.

Also, JSON Schema `if`/`then` failures flow through the existing agent schema
validator as blocking findings. An advisory check must be implemented as an
explicit advisory `Finding`, not presented as a schema conditional unless the
intended severity is blocking and a named rule grants that authority.

## BLOCK — the rule-schema baseline is not acknowledged

`rule.schema.json` requires `id`, `scope`, `applies_to`, and `evidence`, but
only 5 of the 45 current rule files contain full `id:` front matter. Both
illustrative rules named by the plan currently have provenance-only front
matter. Adding classification fields alone will not make either valid against
the cited schema.

The revision must either normalize the selected rule files to the existing
schema and introduce a real validator, or use a separately validated
applicability registry. Do not call the current tree schema-valid or the new
fields exercised until that path exists end to end.

## BLOCK — quantitative and source claims need correction

- Six of twelve roles are classified in the slice, so **six**, not "remaining
  9," role definitions remain. The stated 49 unclassified total is consistent:
  43 rules plus 6 roles.
- The statement that the three disputed role names have zero mentions across
  current public commissioning docs is false. `quick-reference.md` names all
  three; `install-and-layouts.md:204-205` names Contribution Auditor and
  InfoSec Sentinel. The actual problem is inconsistent activation guidance,
  not total absence.

## WARN — do not publish a partial page as the answer to "which may I remove?"

An 8-of-57 demonstration is a reasonable mechanism proof, but an adopter-facing
page linked from the installation flow could look like the promised selection
guide while leaving 49 artifacts undecided. Either label it prominently as an
incomplete classification pilot and keep the current limitation next to every
entry point, or delay the public installation link until the backfill reaches a
useful complete profile. The full backfill may be delivered in reviewed
batches, but it needs one tracked program-level completion condition rather
than an indefinitely partial catalog.

Please revise the Gate 1 plan and acknowledge these findings before the
governor decides it. I support the underlying catalog objective and the choice
to keep a profile generator out of this tranche.
