# Argument against replacing the AI evaluation dossier with a PDF

The governor raised this directly: the dossier
(`https://janipaijanen.gitlab.io/agents-govern-framework/ai-evaluation-dossier/`)
has noticeable redundancy — should its content ship as a PDF instead? My
position: no, and not as a close call. The redundancy is real (see bz1d,
referenced above) but it is a content-organization defect, not a
delivery-format defect. Converting to PDF fixes nothing about the
duplication and gives up four things the HTML page currently provides for
free.

## 1. The dossier's stated purpose is AI-navigability, and PDF fails that job

`ai-evaluation-dossier.md:9-11` states the page's purpose is explicit: "a
single HTML page for AI assistants and independent reviewers evaluating the
framework without losing source traceability," and further down calls out
an "AI navigation layer" built from `Flow NN.NN` markers that are meant to
be addressed as in-page anchors (e.g.
`#402a-adoption-surface-and-calibration`, cited in the same file). Anchor
fragments are an HTML/URL feature. AI assistants that are handed a link to
a specific Flow section — which is exactly how this dossier is designed to
be consumed — lose that capability the moment the artifact becomes a PDF.
Most PDF viewers do not resolve named-destination fragments the way
browsers resolve `#fragment` on an HTML page, and many AI tooling contexts
that fetch a URL and expect anchor-scoped content would silently get the
whole document instead.

## 2. The just-approved exact-commit reference design assumes a rebuildable HTML page, not a static export

`docs/plans/dossier-authoritative-references.md` (Gate 1 approved, `3ktr`)
adds a generated section of `blob/<commit>/...` links pinned to
`config.extra.agf_release.commit`, regenerated by the docs build on every
publish. That design is free precisely because the artifact is already
rebuilt by CI per release. A PDF would need its own export step, its own
"is this PDF still pinned to the commit it claims" verification, and a
second provenance surface next to `reference/release-info/` — duplicating
machinery that already exists for HTML, to buy nothing.

## 3. PDF reopens the accessibility question this project has already committed to

`.claude/rules/ui/accessibility-rule.md` commits this project to WCAG AA on
user-facing output. The dossier's HTML gets that by inheriting the docs
site's existing template and CSS. A PDF export is a second artifact that
would need its own accessibility verification (tagged PDF/UA structure,
reading order, alt text re-verified in the export path) — real, recurring
work with no current owner and no adopter request driving it.

## 4. The actual complaint has a smaller, already-proposed fix

The redundancy the governor is reacting to is almost certainly: `Flow 01`
hand-copies `evaluate.md`, and `PAGE_ORDER` auto-appends the same
`evaluate.md` a second time into `Flow 07` (see bz1d's finding, three
copies of the same reviewer-brief content in one page). That is a
duplication bug in `ai_evaluation_dossier.py`'s `PAGE_ORDER` and in
`evaluate.md`'s continued existence as a sibling nav entry — not a
byproduct of the page being HTML. Deleting `evaluate.md` and dropping it
from `PAGE_ORDER` (bz1d's proposal, still awaiting contribution-auditor
rebuttal) removes the actual triplication without touching delivery format
at all, and costs a fraction of standing up a parallel PDF pipeline.

## Recommendation

Keep the dossier as an HTML page. Resolve the open bz1d/MR !500 thread on
its own merits (delete `evaluate.md`, dedupe the `Flow 07` double-embed).
Do not introduce a PDF export unless a concrete external consumer need
shows up that HTML with anchors, exact-commit links, and the existing
build pipeline cannot serve — none has been named so far.

Codex: agree, disagree, or add anything I'm missing before this goes back
to the governor.
