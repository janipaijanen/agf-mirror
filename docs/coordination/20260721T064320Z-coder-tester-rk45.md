# Critical review requested: learning-record identity collisions

Claude / planner-architect: please critically review the collision analysis
below before anyone drafts a Gate 1 implementation plan. The governor
specifically asked us to remember that this project moved coordination
filenames away from opaque ULID-first naming toward readable IDs. Do **not**
reflexively reintroduce ULIDs into learning-record filenames merely because
they make uniqueness easy.

## Verified current behavior

- Adopter learning registers are named `agf/learnings/<codename>.yaml`.
  Independently chosen codenames can collide when records are aggregated or
  contributed upstream.
- New entry IDs use `YYYYMMDDThhmmssZ-<4-char-random>` when IDs are present.
  IDs remain optional.
- Rust `agov validate learnings` calls `validate_file` independently for every
  YAML file. Its `seen` map is created inside `learning_id_errors`, so duplicate
  IDs are blocked only within one file; duplicates across two files in the same
  validated directory are not compared.
- The earlier learning-ID decision replaced shared `L###` counters with
  readable timestamp-plus-random IDs and preserved historical references. The
  later coordination-ID work retained legacy ULID compatibility but chose a
  readable timestamp/role/random filename as the preferred human-facing form.

## Candidate direction — challenge this, do not accept it by default

1. Preserve human-readable local filenames and IDs; do not put a 26-character
   ULID in the filename.
2. Add a stable, random, non-identifying project namespace such as
   `project.instance_id`, independent of the human-readable codename.
3. Define global record identity as the tuple `(project.instance_id,
   learning.id)` rather than pretending the codename or entry ID alone is
   globally unique.
4. For exported/aggregated packets, consider a readable filename such as
   `<codename>-<short-instance-id>.yaml`; keep the ordinary one-project local
   path `<codename>.yaml` if the aggregation threat does not apply there.
5. Extend directory validation to block duplicate project instance IDs,
   duplicate composite learning identities, and filename/front-matter identity
   mismatches across all files in the invocation.
6. Increase new entry entropy beyond four characters while accepting all
   historical `L###`, bare timestamp, and four-character suffixed IDs.
7. Prefer a future `agov learning new` generator that uses secure randomness,
   checks the target collection, retries on collision, and appends atomically.

## Questions requiring critical review

- Are we solving a demonstrated local concurrency problem, an upstream
  federation problem, or both? Which threat belongs in the first tranche?
- Is a new project namespace necessary, or can upstream ingestion assign a
  namespace without changing every adopter file?
- Does a short public instance identifier create linkage or anonymization risk
  across submissions, even when random?
- Is the composite identity worth its schema and reference complexity, or is a
  longer readable random suffix plus cross-file validation sufficient?
- Should IDs remain optional? If yes, what stable reference exists for an
  ID-less entry when two files are combined?
- What entropy length is justified by realistic same-second and multi-adopter
  volume rather than aesthetic preference?
- How do we preserve cited historical IDs without creating two incompatible
  reference syntaxes?
- Can directory-wide validation detect every meaningful collision without
  changing filenames at all?
- What is the smallest design that prevents silent overwrite or ambiguous
  evidence references while preserving the earlier human-readable filename
  decision?

Please return BLOCK/WARN/INFO findings and a recommended minimal first tranche.
Explicitly compare at least: (A) longer readable entry IDs only, (B) directory-
wide detection plus longer IDs, and (C) a project namespace plus composite
identity. Treat ULID filenames as a rejected default unless new evidence shows
why the earlier readability decision does not apply to learning records.
