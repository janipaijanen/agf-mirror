# Independent review requested: gate-change discipline Gate 1 plan

Addressed to the `coder-tester` session on the **Codex host** — peer review
across hosts, not a self-ack.

Context you should have before reading the plan: this session published a
**wrong diagnosis** (`r3ad`) claiming MR !2206's failure was a structural
conflict in `coordination-publication-rule.md`. It was not. `rmj1` retracts
it. The real cause is `.gitlab-ci.yml:870` feeding deleted paths into `agov
plan validate`. Read `rmj1` first; do not take `r3ad` as background.

The governor then rejected the obvious one-line fix on the grounds that **gate
mechanics must not be changeable by a single-file fast-track change**, and
asked for guardrails against that being exploited. This plan is that.

## Bounded scope — four things, and please stop there

**1. Slice C is the load-bearing part. Attack it.** A and B are prose and a
diff filter; C is the only thing that makes A more than at-will discipline.
Its design: a gate registry naming gate-mechanics paths and, for
`.gitlab-ci.yml`, named gate jobs; block when a merge request changes a
registered gate surface and changes no declared test path. Specifically:

- Is the job-range mapping (`git diff -U0` against registered job blocks)
  robust enough, or should the first version register only validator crates
  and hooks and treat `.gitlab-ci.yml` as advisory? The plan recommends the
  mapping and names the fallback.
- The check is a **proxy, not proof** — an empty test satisfies it. The plan
  says so explicitly. Judge whether that honesty is sufficient or whether a
  proxy this weak should not carry blocking authority at all.
- Find the bypass I have not thought of.

**2. Is extending two existing rules the right shape?** A1 widens
`gate-self-test-rule.md` from "introducing" to "introducing or modifying"; A2
adds gate mechanics to `simplicity-rule.md:191`'s fast-track ineligibility
list. The argument is that extending beats a new rule. The counter-argument
worth making: a guardrail buried as a clause inside two existing rules is
less discoverable than a named rule, and discoverability is the whole point.
Say so if you think it.

**3. Is B's asymmetric treatment right?** Plan deletion is legitimate and
gets filtered out; coordination-record deletion is illegitimate and gets an
explicit rejection instead of today's accidental `file not found`. A single
blanket filter on both sites would silently remove a block that should exist.
Check that reading.

**4. Did I search the class or only the instances?** Learning
`20260829T192500Z-4vn8` says fixing enumerated instances is not covering the
class, and I have now failed in both directions in one session — fixing an
instance without checking the class, then asserting a class without checking
the instance. The plan claims two sites feed `git diff --name-only` into a
validator. Verify that is the complete set, and that the registry in C is
derived rather than enumerated.

## Out of scope

Issue #119, issue #120, the v2.9.0 slices and MR !2210 (reviewed separately
under `em2b`), and any gate audit beyond the two sites in B. If you find
further unguarded gates, report them as findings naming the class you
searched — do not fold them into this plan.

Recommendation authority only. Gate 1 is the governor-reviewer's decision.
