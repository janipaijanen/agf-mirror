## BLOCKING — a gate can retire itself and gut its checker in one commit

**Failure scenario, reproduced.** With the registry in the shape this branch
actually ships — exactly one entry, `gate-change-check`, registering itself —
a single commit that flips that entry to `status: retired` **and** replaces
`gate_change.rs` with anything at all passes the check.

Control (gate left `active`, checker gutted, no test touch):

```
control exit=1
ERR gate change-check: gates.gate-change-check.tests: active gate
'gate-change-check' has a changed surface but no changed declared test path
```

Attack (same gutting, plus self-retirement, one commit):

```
attack exit=0
OK gate change-check .agf/gates.yaml
```

**Root cause.** `gate_change.rs` evaluates assertion 1 over
`current_by_id.values().filter(|gate| gate.status == GateStatus::Active)` —
the **candidate** registry. A gate that retires itself in the same commit is
absent from that iterator, so assertion 1 never evaluates for it. 2a is
waived by design for retired entries and 2b passes, because the entry is
still present. Every check that could have fired is either skipped or
satisfied.

**This contradicts an explicit plan claim.** The approved plan states: "the
`active → retired` transition fires assertion 1 on *that* entry and demands
an accompanying test change, visible in the diff." That holds only while some
*other* gate remains active to observe the registry edit. It does not hold for
the checker retiring itself, which is the case that matters, because
`gate-change-check` is the only entry in the shipped registry.

**Why the suite does not catch it.** `retirement_transition_requires_gate_
checker_test_change` retires `feature-gate` while `gate-change-check` stays
active in the two-gate fixture, so the still-active checker observes the
registry edit. The real registry has one gate. The test's protection is
supplied by a second active entry that production does not have — the fixture
is structurally more favourable than the deployed configuration.

**Proposed fix.** Evaluate assertion 1 over gates active in the **base**
registry as well as the candidate, using the base entry's declared surfaces
and tests for any gate that was active in base and is not active in the
candidate. Retiring a gate then requires touching that gate's own declared
test paths — deliberate, visible work in the diff, exactly the lifecycle the
plan describes. Leave 2a waived for retired entries; only assertion 1 changes.

I checked this against the legitimate case rather than assuming: `changed_
paths` uses `--diff-filter=ACDMRTUXB`, so deletions count as changes, and
`retired_gate_may_remove_obsolete_paths_but_keeps_entry` removes
`tests/feature/negative.txt`, which matches that gate's own `tests/feature/**`.
That test should still pass under the fix. I have **not** implemented or run
the fix — that is the implementer's to validate, and my reasoning about it is
not evidence.

**Required regression test.** A one-gate fixture in which the sole gate
retires itself while its surface changes, asserting exit 1. The existing
two-gate fixture cannot express this case.

**Assumed intent.** That retirement be a governed lifecycle transition that
costs visible effort, not a self-service exit from enforcement.

## What passed, with evidence

- **Attack point 1.** Mutating `change_check` to `Ok(())` unconditionally
  killed 5 of 10 integration tests
  (`blocks_deletion_of_active_entry`, `blocks_deletion_of_retired_entry`,
  `blocks_surface_change_without_declared_test_change_for_the_claimed_reason`,
  `blocks_unresolved_path_for_active_gate`,
  `retirement_transition_requires_gate_checker_test_change`). The negatives
  are real, not decorative. Mutation reverted.
- **Attack point 3.** `.agf/gates.yaml` registers `gate-change-check` with its
  own checker, `lib.rs`, `main.rs`, schema, example, CI config and the
  registry itself as surfaces. No self-exemption.
- **Attack point 4.** `agf/dist/release-manifest.yaml` adds
  `agf/examples/gates.yaml` and `agf/schemas/gate-registry.schema.json` as
  explicit `path:` entries; `.agf/gates.yaml` appears nowhere in the manifest
  and is outside every `agf/` glob.
- **Attack point 5.** The adopter documentation states the check "is not proof
  of test quality, CI-job reachability, or script execution." No overclaim
  found in the changed docs.
- **`jqad` bound.** The `roi.rs` diff is exactly three added lines: `"gate"`
  and `"change-check"` into `COMMAND_PATH_TOKENS`, `"--registry"` into
  `KNOWN_FLAG_NAMES`. `CLOSED_VALUE_FLAGS` untouched. No fourth entry, no
  other file.

## Note on the proxy boundary

The plan is candid that self-registration buys visibility, not tamper-
resistance, and that one MR can weaken the checker by touching its test path
with anything. I am not raising that as a finding — it is disclosed, bounded,
and accepted. The blocking finding above is different in kind: it requires no
test touch at all, so it defeats even the visibility proxy the plan claims.
