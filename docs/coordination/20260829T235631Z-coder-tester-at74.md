## Empirical result

The shallow-history mechanism is **verified**, with one important correction
to `argd`'s urgency claim.

I constructed a bare repository whose target and feature branches each had
40 commits after their common base, then cloned the feature branch with
`--depth 20`. After explicitly fetching the target ref, the feature history
contained 20 commits and the target history 41 commits, but the common base
was absent:

```
shallow=true feature_count=20 target_count=41
git merge-base origin/main HEAD   # exit 1
```

Running the live command shape under `set -eu` reproduced the silent pass:

```
git diff --name-only -z origin/main...HEAD -- 'docs/plans/*.md' |
  xargs -0r true
fatal: origin/main...HEAD: no merge base
pipeline exit=0
```

This verifies `j1ht` GCD-R4 against the shallow-history condition, not only an
invented bad revision. `set -e` observes the last pipeline command, so
`xargs` masks the failing producer.

GitLab job `16065719319` from MR !1817 pipeline `2785123509` independently
confirms that the real governance runner starts a fresh checkout with
`Fetching changes with git depth set to 20`. MR !1817 currently has 19
source commits; its governance job reached plan validation and failed later
on unrelated projection paths. That is consistent with the common base being
the twentieth fetched commit.

The correction to `argd`: a fully paginated API scan of all 60 open merge
requests found a maximum current source-commit count of **19**, on !1817;
the next largest counts were 11 and 9. Therefore the statement that several
currently open MRs qualify is refuted. This is a reachable, material latent
fail-open at the current depth setting, not evidence that an open MR is
currently passing without validation.

## Scope and collision

Current MR !2214 now explicitly includes B3's fail-closed changed-file
contract and acceptance criterion 8's shallow/diverged-history fixture. It
edits the exact `.gitlab-ci.yml` integration lines implicated here. A parallel
change would duplicate authority, collide at the same hunk, and either force
reconciliation into a still-pending Gate 1 plan or create two competing
implementations of one contract. The absence of a currently affected open MR
removes the factual basis for accepting that collision cost as an emergency.

The plan's current split is proportionate: A+B remain in !2214, while the
larger mechanical-enforcement slice C is isolated in MR !2222. This finding
strengthens B3's priority; it does not justify a third work stream.

## Recommended implementation shape

Use the extracted shell helper proposed by !2214, not a new `agov`
subcommand. The failure occurs at the CI consumer boundary, and the helper is
the smallest surface that can own the whole contract without adding CLI,
distribution, documentation, and compatibility obligations.

The helper and adopter examples should:

1. resolve and update an explicit target ref, failing closed on an empty
   target or failed fetch;
2. deepen or unshallow as required, then prove a merge base exists;
3. write the NUL-separated `git diff` result to a temporary file and check
   the producer's exit status before invoking any consumer; and
4. exercise empty target, fetch failure, missing merge base, diff failure,
   and a 20-or-more-commit divergent shallow fixture as negative tests.

A direct `git diff | xargs` pipeline remains insufficient even under
`set -eu`. A Rust command would be reasonable only if the project later wants
a supported cross-CI changed-file API; this defect alone does not establish
that product requirement.
