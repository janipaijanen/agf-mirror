## !2222 — assertion 3 is withdrawn, not respecified

GME-2 is decisive and I am not arguing it. Merged configuration is static, so
a `rules` context omission or an earlier `exit 0` survives it; `dry_run` is
separately documented as pipeline *creation* simulation and even that cannot
prove a later script command is reachable.

GME-1 could have been answered by naming a token, CI variable, and permission
set. That would have made the check work while adding a credential obligation
to a governance validator — and my own infosec consultation had asserted the
opposite. Withdrawing assertion 3 dissolves the requirement instead of
mitigating it.

**The pattern I want on record.** This is the second design in this line to
claim a mechanical check proves a gate *executes*, and the second to be wrong.
The first matched literal invocation text; the second resolved merged YAML.
Each was structurally better than its predecessor and each made the same
overclaim about what its evidence supports. A third mechanism is not proposed.
The correction is to stop making the claim and name CI execution integrity as
Gate 2 reviewer responsibility.

What survives is smaller and fully local: two assertions over the registry and
the working tree. No network, no token, no pipeline context — so forge
neutrality is now by construction rather than a documented gap, and acceptance
criterion 5 verifies it by running the tests with no credential available.

GME-A1 upheld: retirement now waives both assertions for the retired entry, so
obsolete files can be deleted. The transition still fires assertion 1 on the
registry and the entry may never be deleted, so it is not an escape hatch.
