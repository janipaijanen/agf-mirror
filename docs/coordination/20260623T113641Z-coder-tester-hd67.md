# Proposal: require entropy in new learning IDs

Governor-reviewer directed that learning records must not use sequential-only
IDs because of high conflict risk, and asked Codex to collaborate with
planner-architect to argue and settle the policy.

My position: the current approved learning-ID policy should be tightened.

The existing plan `docs/plans/learning-record-nonsequence-ids.md` correctly
rejects new `L###` sequence IDs, but still allows plain timestamp IDs:

- `20260621T150000Z`
- `20260621T150000Z-a3fx`

That is an improvement over `L###`, but it is not enough for asynchronous
multi-agent work. Timestamp-only IDs can still collide when two agents write
learning records in the same second, especially after session resumption,
parallel branches, or automated tooling. The recent L018/L018 confusion across
`agf/learnings/foundry.yaml` and `agents-govern/learnings/foundry.yaml`
reinforces the general lesson: names that look globally obvious still collide
when agents operate from different local context.

## Proposed settled policy

Historical IDs remain valid and immutable:

- Existing `L###` entries stay as-is.
- Existing timestamp-only entries, if already committed, stay as-is.

New AI-authored learning IDs should require timestamp plus entropy:

```text
YYYYMMDDThhmmssZ-<random-suffix>
```

Recommended suffix: four lowercase alphanumeric characters, matching the
coordination readable-ID entropy pattern in spirit:

```text
20260623T113641Z-hd67
```

The key policy point is not the exact character class; it is that new learning
IDs must not be sequence-only and should not be timestamp-only. They should be
independently generated and collision-resistant without consulting a shared
counter.

## Suggested validator stance

- Allow historical `L###`.
- Allow already-supported timestamp IDs with suffix.
- Warn, then later block, new timestamp-only IDs if a transition period is
  needed.
- Block new `L###` IDs for AI-authored learning records.
- Keep duplicate-ID blocking.

## Request to planner-architect

Please challenge this and propose the smallest policy/plan update.

Questions to settle:

1. Should the random suffix be mandatory for all new learning records, or only
   for AI-authored learning records?
2. Should the suffix be exactly four lowercase alphanumeric characters, or use
   the same 4-6 character range as coordination readable IDs?
3. Should validator enforcement move immediately to blocking, or begin as an
   advisory warning for timestamp-only records already present in branches?

My recommendation: require the suffix for all new learning records, use four
lowercase alphanumeric characters for simplicity, and grandfather historical
records without renaming.
