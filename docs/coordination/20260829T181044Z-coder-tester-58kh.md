# Propose a calm AGF explanatory-visual system, then test whether DOT can share it

The governor likes the visual language of [Building Autonomous Goal Loops That
Deliver](https://jx0.ca/building-autonomous-goal-loops-that-deliver/): calm,
clear, aesthetically restrained diagrams for concepts, operations, data flows,
and responsibility flows. They also asked whether the same direction can be
adopted by generated DOT files.

This handoff requests planning and critique only. It does not authorize a site
redesign, generator implementation, or edits to existing figures.

## What is worth learning from the reference

The useful properties are compositional, not a palette to copy:

- a narrow reading field and generous whitespace;
- one primary claim per figure;
- thin neutral structure with sparse accent colour;
- direct labels and short monospace micro-labels;
- clear containment, direction, and hierarchy;
- figures that include an accessible title/label and a prose caption;
- very few decorative elements competing with the explanatory path.

Do not copy its SVG source, exact colour set, font, or branded appearance.
AGF already avoids external font dependencies and has an established
colourblind-safe semantic palette. Treat the page as an observable design
reference, not evidence for an AGF claim.

## Proposed architecture to challenge

### 1. Keep meaning separate from presentation

Preserve the current responsibility/status semantics: human, AI, automation,
shared work, and reference state must remain distinguishable through shape,
line style, labels, and accessible text rather than colour alone.

Add a separate presentation grammar for canvas, neutral text and lines,
accent strength, spacing, typography, corner radius, path emphasis, captions,
and responsive behaviour. Calmness should come mainly from hierarchy, space,
and fewer saturated fills, not from reducing contrast or erasing semantic
distinctions.

### 2. Use the right native format

Do not turn "apply this to DOT" into "force every visual through DOT":

- DOT is a good canonical source for node-edge processes, dependencies, data
  movement, and responsibility handoffs.
- Purpose-built accessible SVG is appropriate for concentric loops, layered
  boundaries, or other spatial explanatory models that Graphviz expresses
  poorly.
- HTML/CSS or a table is preferable when the content is essentially a small
  comparison rather than a graph.

All formats should implement the same semantic and presentation tokens where
their medium permits it.

### 3. Pilot before migration

Propose a first work order that defines the grammar and redesigns only three
high-value figures covering distinct jobs:

1. `governed-change-flow` for the home-page operational story;
2. `operating-responsibility-map` for authority/responsibility flow;
3. `coordination-channel` or `runtime-governance-boundary` for evidence/data or
   system-boundary explanation.

The pilot should include both site embedding and standalone/openable figures.
It must not revive the deferred navigation slice or become a wholesale Pages
redesign.

### 4. Make DOT generation a second work order

If the pilot succeeds, route a separate work order that unifies the existing
`docs/TODO.md` academic-DOT-generation item with the visual grammar instead of
creating a second generator.

The preferred target is a deterministic semantic graph model in Rust that
emits readable, committed DOT with stable ordering and explicit attributes.
Rendering profiles may then produce web-light, web-dark, and print outputs
from one semantic input. The generator should emit DOT; a pinned Graphviz tool
in CI can render it. Generation twice should be byte-identical, and committed
DOT/SVG pairs should have a mechanical drift check.

The plan must decide whether theme variants justify their storage and review
cost. Current standalone SVGs deliberately use fixed white backgrounds and
explicit hex values; changing that is a governed contract change, not a CSS
tweak. A single neutral standalone treatment may be the better minimum.

## Acceptance evidence to include in the plan

- A short diagram grammar for concept, operation, data/evidence, and
  responsibility/authority figures.
- Every figure retains a useful title, description or ARIA label, prose
  caption, non-colour semantic cues, and standalone legibility.
- Embedded labels remain readable at representative narrow and wide viewports;
  no page-level horizontal scroll and no blind shrink-to-fit. Use local scroll,
  reflow, an alternate composition, or a full-size link deliberately.
- Light, dark, and print behaviour is explicit even if the decision is to ship
  only one standalone theme in the pilot.
- DOT parses and renders using the pinned toolchain; generated output is
  deterministic and has no runtime font/CDN dependency.
- Existing contrast and colour-vision checks remain green.
- Independent `web-ux-reviewer` review compares the old and pilot figures for
  hierarchy, readability, and mobile behaviour.
- A small comprehension check with the target reader (third-year ICT
  engineering level) asks what changed, who decides, what evidence moves, and
  where the boundary lies. This makes "calm and clear" testable rather than
  only a taste claim.

## Explicit exclusions

- no exact visual imitation of the JXØ page;
- no decorative gradient as a semantic code;
- no external webfont or JavaScript-only/canvas dependency;
- no migration of all thirteen existing DOT/SVG pairs in the pilot;
- no promise that one renderer can express every explanatory figure well;
- no release commitment until the work orders and gates exist.

## Requested planner response

Please argue against this split before adopting it. In particular:

1. Is three pilot figures still too much for one Gate 1 work order?
2. Is a multi-profile DOT generator worth its maintenance cost, or should the
   first generator support one neutral standalone profile only?
3. Which visual properties can be made objective without turning the grammar
   into arbitrary numeric limits?
4. Does any part collide with the approved v2.9.0 release work order or the
   deferred Pages navigation slice?

If the direction survives those questions, return a bounded plan proposal and
the order in which contribution-auditor, web-ux-reviewer, and build-engineer
should be consulted. Do not implement before a binding Gate 1 decision.
