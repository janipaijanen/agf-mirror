# INFO — post-v2.3 proposal: distinguish MCP from direct CLI telemetry

Current `agov-mcp` tools launch the corresponding `agov` CLI subprocess. When
ROI logging is enabled, the child records the underlying command, but the JSONL
record cannot distinguish a direct CLI invocation from an MCP-mediated one.

Please critically review a post-v2.3 improvement that adds only low-cardinality
transport provenance, for example:

```json
{
  "implementation": "rust-agov",
  "transport": "mcp",
  "adapter": "agov-mcp",
  "tool": "agov_coord_validate",
  "command": "agov",
  "args": ["coord", "validate", "..."]
}
```

Direct shell invocation would record `transport: "cli"`; existing readers must
remain compatible when the new fields are absent.

## Hard privacy boundary

The design MUST NOT write any of the following to disk:

- MCP client identity or client metadata;
- session, conversation, correlation, or request IDs;
- user or assistant prompts;
- model responses;
- raw JSON-RPC envelopes;
- environment values that could identify a user, host, or client instance.

The proposal is transport attribution, not request tracing. Values should come
from a small controlled vocabulary set by the trusted local adapter for the
child process, not copied from untrusted MCP request fields.

## Questions for Claude

1. Should the adapter pass fixed child-process environment markers, or should
   `agov-mcp` append a separate sanitized telemetry event?
2. How can direct CLI remain the default without letting arbitrary callers
   spoof MCP attribution through public environment variables?
3. Is recording the fixed MCP tool name useful enough, or are `transport` and
   `adapter` sufficient and safer?
4. Should command arguments remain recorded under the existing policy, or does
   MCP mediation create an additional argument-redaction requirement?
5. What schema/versioning and tests ensure old JSONL readers ignore the new
   optional fields?
6. Should this become a Gate 1 plan after v2.3, or remain deferred until real
   telemetry comparison needs justify implementation?

This is explicitly **not planned for v2.3.0** and must not delay its release.
Return requires-ack BLOCK/WARN/INFO findings and recommend the smallest safe
future tranche. Do not implement the change in this review.
