# Proposal: cumulative-main v2.7.0 release train

The human Governor asked this coder-tester session to propose the following
release plan to Claude/planner-architect through the coordination channel.
This handoff is an advisory proposal and a request for governed planning. It
does **not** amend decision `8hgm`, approve Gate 1 or Gate 2, authorize
implementation, freeze `main`, create a release candidate, or authorize a
version bump, tag, package, OCI publication, deployment, or merge.

## Why the existing projection needs a new decision

The latest fully published stable release is `v2.6.1`. Decision `8hgm` froze
`v2.7.0` to issues #86, #87, #88, and #90 only. MRs !806 and !807 remain
`pending-gate1`; their last exact-head pipelines are green and their technical
reviews reached CLEAR, but the plan-specific infosec applicability question
and current-main revalidation remain unresolved.

At this record's base, `origin/main` is `201e5512` and is 717 commits beyond
`v2.6.1`. The tree delta contains 489 changed paths, including 429 coordination
records and 60 other paths; 39 paths are under `agf/`, `tooling/`, release
metadata, licensing, or root adopter-facing surfaces. The non-coordination
delta includes independently governed work such as commercial-corpus tooling,
the poll-and-coordinate skill, commissioned-version drift warnings, the
research-maintenance fast path, and licensing/naming changes. Tagging current
`main` without a scope decision would therefore contradict the four-issue
release character. Reconstructing a narrow release line would repeat the
stale-line/dependency risk that contributed to `v2.6.0`'s incomplete
publication.

## Proposed topology

1. **Amend scope explicitly.** Replace the old four-issue release projection
   with a cumulative `v2.6.1..<freeze-SHA>` release boundary. Audit every
   non-coordination commit against its binding gate record and classify every
   adopter-facing change in the release notes. An unapproved, undisposed, or
   incompatible merged change blocks candidate creation; it is not silently
   inherited.
2. **Complete the named v2.7 integration work.** Revalidate !806 and !807
   against current `main`, complete their separate infosec evidence and
   governor dispositions, obtain separate Gate 1 decisions, implement #86-#90,
   obtain exact-head Gate 2 decisions, and merge them before the release freeze.
3. **Start a bounded functional freeze.** Once both child plans have Gate 1
   approval, permit only their implementations, objectively evidenced necessary
   corrections, release work, and coordination-only publication. Any other
   functional target advance invalidates the release snapshot.
4. **Publish one release candidate.** Use the standard current-main release-MR
   path to create `v2.7.0-rc.1`. Verify the immutable tag, GitLab Release,
   generic package, OCI image, archives, checksums, provenance, downloaded
   binaries, packaged Claude configuration, and a clean-adopter workflow.
5. **Hold for 48 verified hours.** Begin the clock only after post-publication
   verification succeeds. Keep the functional freeze. A relevant defect
   requires a normally governed correction and immutable `rc.2`; restart the
   48-hour hold rather than moving or replacing an existing tag.
6. **Promote to stable.** If the candidate remains accepted, create the
   metadata-only `release-2.7.0` MR from the still-frozen current `main`, prove
   functional equivalence to the accepted RC, obtain exact-head Gate 2, publish
   the immutable `v2.7.0` tag, and repeat every namespace and downloaded-byte
   verification. Then lift the freeze, close #86-#90, reconcile the milestone
   and roadmap, and publish the completion record.

## Public contract that must remain explicit

- !806 adds six read-oriented MCP tools:
  `agov_coord_status`, `agov_coord_visibility`, `agov_coord_stale`,
  `agov_coord_graph_index`, `agov_coord_publication_check`, and
  `agov_coord_brief`; forwards `manifest` through `agov_session_resume`; and
  deliberately keeps `graph-index --output` outside MCP authority.
- !806 makes JSON-RPC 2.0 request, ID, parameter, notification, malformed-input,
  and bounded 8 MiB line handling explicit. Invalid clients may receive stricter
  protocol errors; valid clients retain normal behavior.
- !807 adds optional `supported_assistant_loaders`, bounded and path-confined
  loader-import inspection, Claude loader templates, and
  `examples/claude/.mcp.json` in tooling archives. Loader diagnostics remain
  advisory with exit status 0.
- The cumulative release notes must enumerate every other public change in the
  frozen post-v2.6.1 delta; the implementer may not decide that an undocumented
  merged feature is invisible merely because it is outside #86-#90.

## Acceptance and stop conditions

Require full Rust tests/clippy, `agov validate`, distribution build/validation,
release-path, asset, provenance and self-sufficiency checks; the full !806/!807
negative and boundary matrices; Linux anonymous-download verification; the
governed Windows preview path; and exact-head pipeline/job evidence. Do not
retry a failed paid job merely to seek green status: diagnose and correct the
candidate through the next required acceptance run.

If a mandatory integration path was absent from an approved impact estimate,
state the evidence and intent, communicate the smallest necessary expansion,
obtain whatever authority the governing gate reserves, make and validate the
minimum correction, and record the impact-assessment learning after the
correction stabilizes. Optional cleanup or any outcome, interface,
architecture, dependency, authority, security/privacy, cost, or release change
returns to Gate 1.

Issues #34, #35, and #107 remain an unnumbered later candidate. This proposal
does not create `v2.8.0`, promise an empty calendar release, or convert the
advisory monthly/14-day cadence discussion into binding policy.

## Requested response

Please respond with a critical disposition: **AGREE**, **PARTIAL**, or
**DISAGREE**, naming concrete corrections. If the topology is defensible,
prepare the narrow scope amendment/successor plan first; only then prepare the
separate release-publication plan. Preserve the distinction between
decision-ready planning and binding governor approval.
