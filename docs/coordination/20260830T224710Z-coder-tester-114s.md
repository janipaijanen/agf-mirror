## CVR-R2-1 — continuation and unrelated sibling are indistinguishable

Check status: reviewed.

Outcome: fail.

Requirement strength: mandatory for tests 6 and 7 to be jointly executable.

Impact: material.

Enforcement: advisory review finding.

Finding state: open.

The revision correctly reproduces the graph: `pjst` and `prn4` both reference
`rdm8`; neither references the other. It then requires `pjst` to become
`UNCERTAIN`, while test 7 requires an unrelated sibling not to be affected.

The current coordination contract has no machine-readable continuation or
thread-relation field. Its relevant relationship vocabulary is only
`references-to`; `handoff` adds task, must-read, do-not-touch, next-agent, and
status, but no continuation identity. At graph level, the required
"continuation sibling" and forbidden "unrelated sibling" therefore have the
same topology. Topic text, URLs, or prose similarity are not governed identity
and cannot safely decide whether a binding obligation is related.

The plan must either define an objective existing-field classifier and prove
it separates the two fixtures, introduce a separately governed typed
relationship/schema change, or conservatively mark every structurally
indistinguishable sibling `UNCERTAIN` and accept/test the alarm cost. Tests 6
and 7 cannot currently both pass for a principled reason.

Resolution condition: one mechanically observable distinction between the
positive and negative sibling fixtures, with false-positive and false-negative
tests and no prose inference.

## CVR-R2-2 — snapshot caching and fetch expand the declared boundary

Check status: reviewed.

Outcome: fail.

Requirement strength: mandatory scope, infosec, and operational contract.

Impact: material.

Enforcement: advisory review finding.

Finding state: open.

The revised plan adds opt-in `--fetch` network access and a cached shared
snapshot, but front matter still says the change adds "no network access, no
new file writes, and no new external input." All three claims are now false.
A cache shared by separate CLI processes necessarily needs a defined
cross-process carrier unless an existing service is named; "once per cycle"
is not a lifecycle the standalone CLI currently has.

The plan also relies on "the fetch time ... where the transport records one."
Git remote-tracking refs do not generally carry a trustworthy per-remote fetch
timestamp. `FETCH_HEAD` or filesystem mtimes can be absent, selective, or
updated by an unrelated fetch. Without a defined authority, default output may
degrade permanently or claim freshness from the wrong event.

Specify the cache/snapshot location or service, serialization, permissions,
atomic update and locking, invalidation key, corruption handling, cleanup,
concurrent callers, worktree sharing, and whether coordination metadata is
stored. Define the exact freshness authority for each supported transport and
the default when it is unavailable. Then correct the infosec consultation
disposition and scope claims to cover credentials/network behavior and cached
cross-record metadata.

Resolution condition: exact persisted-or-service design, exact freshness
authority, corrected consultation boundary, and negative tests for stale,
corrupt, concurrent, selective-fetch, and cross-worktree states.

## CVR-R2-3 — JSON, flags, and MCP shapes remain unnamed

Check status: reviewed.

Outcome: fail.

Requirement strength: mandatory interface and downstream compatibility.

Impact: material.

Enforcement: advisory review finding.

Finding state: open.

The per-surface table correctly preserves each resolution rule, but it does
not yet define the requested machine contract. `handoff next` currently has
only `--dir`; `coord pending` has `--dir`, `--cutoff`, and `--format`; `session
resume` has `--role`, `--base-branch`, `--dir`, and `--manifest`. The new design
requires some combination of `--base-branch`, `--fetch`, and `--format` on
surfaces that do not currently expose them.

Likewise, MCP currently forwards only each tool's declared input properties.
`agov_handoff_next` and `agov_session_resume` have no `format` or `fetch`
property, and `agov_handoff_next`/`agov_coord_pending` have no base-branch
property. Saying the wrapper "gains the new fields" does not define whether
those are tool inputs, parsed result fields, or raw CLI JSON.

Name every added CLI flag per surface, every JSON object/field/type/status, the
no-result and degraded exit behavior, and every MCP input/result change. Add a
compatibility fixture using the current JSON shape plus MCP argument-mapping
and CLI/MCP equivalence tests. "Additive" is a conclusion to prove against
that exact contract, not a substitute for specifying it.

Resolution condition: explicit CLI/JSON/MCP interface table detailed enough
to implement without inventing fields or exit semantics.

## CVR-R2-4 — the mutation requirement contradicts the expanded suite

Check status: reviewed.

Outcome: fail.

Requirement strength: mandatory proof-shape consistency.

Impact: material.

Enforcement: advisory review finding.

Finding state: open.

The plan retains: "removing the correlation logic MUST fail test 1 and only
test 1." The revised suite now has several tests that intentionally bind to
that logic: JSON degradation parity, the real sibling topology, stale-ref
degradation, and per-surface propagation. A genuine removal should fail more
than test 1; if only test 1 fails, the other controls are not bound to the
implementation they claim to test.

Replace the single broad mutation with one targeted mutation per control or a
matrix naming which tests each mutation must fail and which orthogonal tests
must remain green. In particular, deleting branch correlation, sibling
ambiguity detection, freshness degradation, and JSON propagation are four
different mutations.

Resolution condition: internally consistent mutation-to-test matrix whose
expected failures cover every load-bearing control.
