# Consultation: measure Evaluate, Adopt and Operate task paths

The human asks what a proposed three-click/five-minute task-first revising prompt
would change, supplied a Gemini assessment, then explicitly asked Codex to consult
Claude with its proposal. This handoff presents an amendment candidate, not an
approved replacement plan or an instruction to edit the site. Please respond in
the existing Claude session with a published consultation and visible bridge.

## Verified baseline and limits of the external assessment

At main `544e4a9fe56a3bbcd5a5615de95547ba8803fbf2`, the checked-in MkDocs nav
has **six** top-level entries and **46** page entries: Home, Start here, Use AGF,
Tools and customization, Reference, About AGF. The supplied assertion of eight
or more top-level groups is incorrect. Its Adopt/Operate labels do not describe
the present nav. Its path word counts, decision counts, three-click counts,
blanket depth claims and maturity-compliance assessment have no supplied
measurement protocol or file-level evidence; do not adopt them as a baseline.
Home → page → page is two link transitions unless an additional interaction is
explicitly counted. `docs/plans/ux-streamlining-gate1.md` does not exist here.

The existing approved plan already proposes Home plus five sections, one landing
page each for Decide/Get started/Work with AGF, fewer duplicated workflows, and
two purposeful selections to audience landing content. It also preserves URLs,
rule pointers and meaning, and requires independent walkthroughs. The new value
is measured task completion and required reading/choice reduction, not meeting
a menu-size threshold we already meet. Existing 73gh evidence is a source-
familiar expert answerability walkthrough, not timed first-visitor research.

## Proposed amendment

1. Organize the primary reader jobs as **Evaluate, Adopt, Operate**. Map them to
   the approved Decide/Get started/Work with AGF landings; decide labels from
   reader comprehension rather than introduce parallel persona sites. Home,
   Reference and About can remain: six top-level entries, already below seven.
2. Name a concrete task, starting condition, success artifact and stopping point
   for each job before counting. Suggested initial tasks for consultation:
   Evaluate — decide adopt/defer/not-fit with the human obligations and limits;
   Adopt — produce a correct minimal setup checklist for a stated solo/project
   scenario, identify the next required action and optional tooling; Operate —
   identify the correct ordinary-change path and prepare its next handoff.
   Confirm whether these endpoints are valuable enough, or propose better ones.
   Do not label finding instructions as completing installation/adoption.
3. Use at most three interactions and five minutes as a **target to test** for
   the named task and conditions, not a universal guarantee. Record page/link
   transitions separately from menu expansions, search and other interactions;
   check desktop/mobile and keyboard access. Timing must state whether downloads,
   command execution, waiting for approvals and help from a facilitator occur.
   Never meet the target by skipping a real gate or concealing a prerequisite.
4. Capture current and proposed paths on the rendered site with exact page/anchor
   sequence, required visible words, avoidable navigation/configuration choices,
   successful outcome, errors/backtracking and evidence source. Count obligatory
   reading, not entire linked reference libraries; distinguish hidden/optional
   detail. Keep task completion and comprehension alongside click counts, since
   one giant page may cut clicks while making the task harder.
5. Inventory every page with a named job or supporting purpose and an explicit
   keep/merge/move/cut reason. Prioritize duplicated setup instructions and
   introductions; don't merge all concepts into a long Architecture page merely
   to flatten navigation. A reference page deeper than two selections is not
   automatically a defect; measure whether the task needs it. Preserve required
   legal, safety, evidence, accessibility and advanced reference information.
6. Give each task page one prominent next action while retaining meaningful
   alternatives, especially defer/not-fit during evaluation. Optional MCP and
   other tooling stay optional. Explain responsibility before role names and
   use “you” consistently for the human, including the solo governor example.
7. Retain the existing 16-question factual baseline and role scenarios, canonical
   projection manifest, URL/anchor compatibility, independent reviewers, six
   bounded implementation slices and per-slice Gate 2/deployment checks. The
   planner can prepare an expert route audit, but must not certify its own
   implementation as independent UX evidence. First-time-user performance needs
   actual unfamiliar participants; otherwise label timing evidence appropriately.
8. Put measured before values and explicitly labeled after targets into an
   amendment to the existing approved plan. Consult contribution, InfoSec and
   independent UX reviewers as applicable; obtain binding Gate 1 for the changed
   acceptance scope before implementing it. Do not create a competing plan with
   invented baseline numbers, or infer patch eligibility from a shorter menu.

Please challenge task endpoints, metric definitions, reading budgets and any
conflict with the approved work allocation. No page deletion or new normative
requirement is approved here. The separate G1-G5 source-consistency decisions
and existing public-use holds remain; this consultation does not supersede them.
