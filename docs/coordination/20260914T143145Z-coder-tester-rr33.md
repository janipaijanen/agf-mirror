## S4-G1-R2-1 — `--changed-only` still lacks a deterministic CI base and can fail open

Check status: reviewed. Outcome: fail. Requirement strength: mandatory.
Impact: material. Enforcement: blocking. Basis: `gate-self-test-rule.md`, the
plan's deterministic-gate claim, and the established fail-closed changed-file
contract already documented in `.gitlab-ci.yml`.

`--plans-only` correctly removes ref inventory from collision candidates, but
`--changed-only` still has to diff plan files against a base ref. Round 2
removed the explicit `--base-ref origin/main` and now relies on the command's
default local ref `main`, saying the MR target is always that branch. The real
runner log for pipeline `2847515773` shows a fresh repository checked out at
`7ac27f1b` as **detached HEAD**. A local `refs/heads/main` is not part of the
job contract. This repository's existing governance job already documents the
same fact and explicitly fetches/resolves the target because common MR
pipeline variables or local refs can be absent.

The proposed exit contract compounds the problem: it says blocking mode exits
0 when no eligible collision exists, even if coverage is incomplete. If the
base cannot be resolved, no plan can be established as changed, so the new
gate can pass without evaluating the candidate plan. `--plans-only` removes
runner-dependent branch inputs; it does not remove this runner-dependent base
input.

Resolution condition: specify a deterministic target-base resolution step in
the CI job (prefer reusing the repository's accepted changed-files/base
contract or an equivalently tested exact-SHA path), pass that resolved commit
explicitly to `--base-ref`, and fail non-zero when the base or merge base
cannot be resolved. Add a job-level negative fixture for an unavailable base
that proves the gate blocks rather than returning clean. Keep intentional
`unassessed` plans separate from operational `unavailable`/`invalid` failures
instead of mapping all incomplete states to success.

## S4-G1-R2-2 — unchanged output cannot carry the blocking severity the rule requires

Check status: reviewed. Outcome: fail. Requirement strength: mandatory.
Impact: material. Enforcement: blocking. Basis:
`agf/rules/always/tool-authority-boundary-rule.md`.

The plan says `--fail-on-unacknowledged-collision` changes only the exit code,
"never the printed report." The existing S3 report labels its final result
`(advisory only)` and does not emit `severity: blocking` on collision lines.
The authority rule requires a blocking check to declare its level and says
undeclared output is advisory. Therefore the proposed job would return a
non-zero process status while its own evidence still describes the finding as
advisory-only. Updating the normative owner does not correct contradictory
runtime output.

Resolution condition: define and test mode-sensitive output. In blocking mode,
every unacknowledged eligible collision used to fail the job must be visibly
`severity: blocking`; acknowledged collisions and coverage notices must carry
their correct advisory/informational level. Default no-flag output can retain
its current advisory semantics. Include the exact labeled negative transcript
in Gate 2 evidence.
