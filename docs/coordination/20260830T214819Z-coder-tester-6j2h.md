## CVR-1 — the claimed base-branch regression is not the graph being reported

Check status: reviewed.

Outcome: fail.

Requirement strength: mandatory for an executable causal plan.

Impact: material.

Enforcement: advisory review finding; Gate 1 remains the governor's decision.

Finding state: open.

The plan says the stale !2181 obligation is `rdm8`, and test 6 specifies a
handoff directly referenced by a later governor decision. The current graph
already handles exactly that shape:

- `prn4` directly references `rdm8`;
- `agov coord graph-index` reports `rdm8` as `resolved: true`;
- the item returned by `agov handoff next governor-reviewer` is instead
  `pjst`, reported as `resolved: false`;
- `pjst` references `rdm8`, while `prn4` also references `rdm8`; neither
  record references the other. They are sibling descendants of the same
  earlier handoff, not the direct relation described by test 6.

A test implementing the plan's current exact wording would therefore pass on
the unmodified code and would not bind to the live defect. The plan must define
the intended semantics for a later continuation handoff and a later resolving
record that names their common ancestor. A safe default is not to infer silent
resolution from siblinghood: require `UNCERTAIN` unless the decision directly
names the continuation, or specify a stronger authorized lifecycle relation
with negative cases proving an unrelated sibling cannot be closed. Replace
test 6 with the actual `rdm8` / `pjst` / `prn4` topology and require the
unmodified implementation to fail it.

Resolution condition: corrected causal model plus a regression fixture that
reproduces the actual stale `pjst` result and rejects false sibling closure.

## CVR-2 — local remote-tracking refs are not a fresh remote view

Check status: reviewed.

Outcome: fail.

Requirement strength: mandatory under the plan's own no-false-clean contract.

Impact: material.

Enforcement: advisory review finding.

Finding state: open.

`coord visibility` enumerates locally available refs. It does not fetch, and
Git cannot prove that a remote-tracking ref is current. Test 4 covers an absent
or unfetchable remote, but not the ordinary stale-ref state in which the remote
contains a resolving record that the local clone has not fetched. In that
state the proposed commands can still return the same definite false-clean
answer the plan claims to eliminate.

The plan must bind every result to a named local snapshot and define the
freshness contract. Options include an explicit caller precondition with a
visible `snapshot-not-verified` degradation, or an authorized fetch mode with
clear network/failure behavior. Add a stale-remote-tracking-ref negative test;
an absent-remote test is not a substitute.

Resolution condition: explicit snapshot/fetch contract and a negative test in
which the remote has advanced but local remote-tracking refs have not.

## CVR-3 — the three command surfaces do not share one compatibility contract

Check status: reviewed.

Outcome: fail.

Requirement strength: mandatory downstream-impact and interface completeness.

Impact: material.

Enforcement: advisory review finding.

Finding state: open.

The plan applies one resolving-kind rule and one JSON requirement across three
surfaces whose current contracts differ:

- `handoff next` uses transitive descendants and only `ack`, `completion`, or
  `decision-record` as resolving kinds;
- `coord pending` deliberately uses a direct reference of **any** later kind,
  under the governed v2.5.0-rc.1 contract;
- `coord pending` already supports `--format json`, while `handoff next` and
  `session resume` do not expose that option;
- the MCP wrappers mirror the CLI and therefore acquire interface work if new
  JSON fields or options are added.

The plan neither preserves nor explicitly changes `coord pending`'s existing
resolution rule, and it does not define JSON field names, status values, exit
codes, backward compatibility, or MCP parity for the two newly structured
surfaces. This is not an implementation detail: it decides whether existing
obligations reopen and whether downstream clients can consume the result.

Resolution condition: a per-surface contract table covering resolution
semantics, text and JSON output, exit codes, MCP behavior, compatibility, and
the exact test files/fixtures that prove each preserved or changed behavior.

## CVR-4 — the hot-path cost acceptance criterion is unbounded

Check status: reviewed.

Outcome: fail.

Requirement strength: mandatory for the plan's default-on design.

Impact: material.

Enforcement: advisory review finding.

Finding state: open.

The risk section says cost must be measured but defines no threshold or
representative corpus. On the current checkout, with 605 `origin/*`
remote-tracking refs, one `agov coord visibility --base-branch main --format
json` run took **23.85 seconds** and exited 2 after finding branch-local
records. Making comparable work default in `handoff next`, `coord pending`,
and `session resume` would put a tens-of-seconds scan on the most frequent
cold-start and polling paths, potentially three times per action cycle.

The plan needs a measurable latency/work budget and a design that avoids
repeating the same full-ref scan across adjacent commands, such as one shared
snapshot/index per cycle or another bounded mechanism. Test with a corpus
representative of this repository's stale and active branch population, not
only a small synthetic repository.

Resolution condition: stated budget, representative scale fixture or
benchmark, and acceptance evidence proving the default path meets it without
silently dropping branches.
