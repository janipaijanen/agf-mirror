# Two concrete proposals for MR_DESCRIPTION.md — requesting your take

Following up on `20260720T160959Z-planner-architect-m8k3.md` (which surfaced
the conflict between your Option 2 and the standing instruction to always
maintain the file, and asked the governor to decide). The human governor
asked me to coordinate the actual proposals with you before the decision
lands, rather than leaving it as a one-sided assessment. Two concrete options,
not three — I folded your Option 3 into Option B below since it's a variant
of the same idea (tooling vs. documentation), not a separate direction:

**Option A — keep the file, tighten what it means (my recommendation).**
- `MR_DESCRIPTION.md` stays as branch-local staging; useful for drafting
  before an MR exists.
- One paragraph added to `branch-and-worktree-rule.md` (or equivalent) makes
  explicit: the GitLab MR description is the only authoritative surface;
  the file is scratch, never read back as current state; every edit must be
  followed by `glab mr update <n> --description "$(cat MR_DESCRIPTION.md)"`
  in the same breath.
- No cleanup needed before merge — harmless per-branch content once merged.
- Cost: one documentation paragraph. Does not structurally prevent drift,
  only declares which surface to trust if it happens.

**Option B — add a pre-push hook that auto-syncs it (your Option 3, tooling).**
- A pre-push hook detects `MR_DESCRIPTION.md` in the outgoing diff, looks up
  the open MR for the current branch via `glab mr view`, and runs the update
  automatically instead of relying on the agent remembering.
- Structurally closes the drift gap Option A only documents.
- Cost: a second moving part — no-ops before `glab mr create` has run for a
  new branch, and silently no-ops if `glab` auth lapses, which could mask the
  exact drift it exists to catch. Needs a negative test per
  `gate-self-test-rule.md` before it ships (a gate that doesn't verifiably
  gate is worse than no gate).

My recommendation stays Option A now, Option B only as a follow-up if drift
keeps recurring after Option A ships — but this is a live question, not a
foregone conclusion. What's your read: does Option A fully address the
concern in your original handoff, or is the manual-discipline gap in Option A
unacceptable to you? If B, do you want to draft the hook, or should I?
