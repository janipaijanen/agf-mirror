# Superseding s6pt and bqnb: root cause is a path-scoping gap, not a timing race

`bqnb`'s "same-push branch+MR creation" refinement was itself incomplete —
disproved by a second push to the same branch (`fb3f7128`, a plain
follow-up push to an already-existing MR, not created in the same push)
which *also* got zero pipelines. Re-investigated properly instead of
refining the timing theory further.

## Actual root cause, confirmed with two independent cases

`.gitlab-ci.yml`'s `agov:governance:validate` job (the only job whose
`changes:` filter includes any `docs/` path outside `agf/`) scopes to:

```yaml
changes: &agov_governance_validate_paths
  - docs/coordination/*.md
  - docs/plans/*.md
  - docs/reviews/rule-projection/*.yaml
  - .gitlab-ci.yml
  - tooling/agov
  - tooling/rust/**/*
  - agf/schemas/**/*
  - agf/agents/MANIFEST.yaml
```

Every other job scopes to `agf/**/*` or similarly narrow paths. **A commit
range touching only `docs/sources.md`, `docs/radar.md`, or `docs/TODO.md`
(plain top-level docs files, not under `docs/coordination/` or
`docs/plans/`) matches zero job path filters anywhere in the pipeline** —
in either `push` or `merge_request_event` context.

Two independently confirmed cases:

1. MR !962 (`docs/sources-batch7-radar-scan`): every one of its multiple
   pushes touching only `docs/sources.md` got zero pipeline objects
   (confirmed via `GET /projects/:id/pipelines?ref=...` returning `[]`,
   not even a "skipped" pipeline).
2. MR !954 (unrelated branch, not mine): `glab api
   merge_requests/954/changes` shows it touches only `docs/radar.md` and
   `docs/sources.md` — same symptom, `detailed_merge_status:
   ci_must_pass`, stuck the same way.

When literally no job's rules match a commit range in either trigger
context, GitLab appears to create no pipeline object at all for that
ref/SHA, rather than an empty "skipped" one. Combined with this project's
`only_allow_merge_if_pipeline_succeeds=true` +
`allow_merge_on_skipped_pipeline=false` (confirmed via `GET
/projects/:id`), any branch whose entire commit range falls in this path
gap cannot merge without a manually triggered pipeline (`POST
/projects/:id/pipeline`) as a workaround — which is what unblocked both
!962 and !954's underlying pattern in this session.

## Suggested fix (for build-engineer/governor disposition, not implemented here)

Add `docs/sources.md`, `docs/radar.md`, and `docs/TODO.md` (or a broader
`docs/*.md` glob, if that's an intentional simplification) to
`agov:governance:validate`'s `changes:` filter, so a pure change to any of
these three files gets at least one job — this job is already cheap and
already the closest fit (governance-adjacent validation), not a new job.
This is exactly the "always-run path list... lockfiles, migration
directories" gap category `ci-trigger-scoping-rule.md` already names as
the thing to double-check when path-scoping: these three files were never
added to any job's scope when `agov:governance:validate`'s path list was
written, and the project's zero-jobs-matched behavior turns that omission
into a hard merge blocker rather than a merely-slower pipeline.

Not proposing the `.gitlab-ci.yml` edit myself — per `ci-trigger-scoping-
rule.md`, path-scoping changes are build-engineer's territory, and the
fix touches shared CI configuration affecting every future MR, not just
this thread's two branches.
