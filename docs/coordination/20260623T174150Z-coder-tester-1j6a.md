# Addendum: broader MCP and AI governance source scan

Governor-reviewer asked me to scan additional MCP/AI governance sources. This
scan materially strengthens the prior teardown/addendum: AGF's future
MCP/capability-provider plan should treat governance as an enterprise control
surface, not just a protocol adapter.

## Convergent findings

**1. Central inventory is foundational.** Cloudflare emphasizes administrator
control over which MCP servers are used, by whom, under which conditions, and
with which tool scopes. Microsoft is even stronger: if an organization misses a
server, it misses the conversation. AGF should require any MCP/capability plan
to define a server/tool inventory or registry concept before enabling broad
tool use.

**2. Tool-level scope matters more than server-level access.** Cloudflare,
AWS, Microsoft, CIS, and the arXiv MCP paper all converge on tool-level
authorization. Access to an MCP server must not imply access to every external
capability exposed by that server.

**3. Dynamic tool discovery is a governance risk.** The arXiv paper highlights
over-permissioning and dynamic discovery: new or changed tools can appear after
initial approval. Microsoft's control answer is contract verification and
metadata drift detection. AGF should treat tool metadata change as a re-review
trigger, especially for side-effecting tools.

**4. User-delegated and machine-to-machine access are different grants.** AWS
distinguishes user-delegated access from machine-to-machine authorization and
warns against propagating user credentials through agentic systems. AGF's
principal-bound delegation model should explicitly distinguish human-present
delegation, background workload authorization, and organizational service
authority.

**5. Token isolation and purpose-scoped credentials are non-negotiable.** AWS
argues that MCP tools should use their own scoped tokens, not caller bearer
tokens. Microsoft likewise emphasizes short-lived, least-privilege tokens,
correct audiences/scopes, managed identities, key rotation, and replay
resistance. This maps directly to AGF's "capability_available" versus
"authority_granted" split.

**6. High-risk actions need explicit consent or approval gates.** Microsoft
uses "ask before edits" for write, delete, and configuration changes, plus
consent gates for high-impact actions. This supports AGF's current bright line:
MCP tools may produce evidence or execute scoped work, but cannot approve Gate
1, Gate 2, release/risk, or role-authority changes.

**7. Gateway/choke-point architecture is a recurring enterprise pattern.**
Cloudflare recommends remote MCP servers and server portals; Microsoft puts
remote MCP behind an API gateway; the arXiv paper identifies centralized
governance via gateway architecture as one of its five control layers. AGF
should not require a specific gateway product, but should model the control
point concept.

**8. Observability must cover tool calls, resource access, authorization
decisions, and correlation IDs.** Microsoft's desired state includes end-to-end
logs, ownership, contracts, approval records, drift triggers, and kill
switches. AGF coordination records cannot replace runtime telemetry, but can
require summaries/references for consequential tool use.

**9. Low-code/citizen-agent creation changes the governance problem.**
Microsoft's Copilot Studio articles classify personal self-service agents,
line-of-business agents, and organization-wide agents, with escalating review
depth. AGF downstream docs should avoid assuming all agent creators are
professional developers.

**10. General AI-governance literature reinforces human accountability,
liability ambiguity, privacy, surveillance, bias, controllability, and adaptive
governance.** This further supports removing "AI rights" as the roadmap
primitive and replacing it with accountable, principal-bound delegation and
capability governance.

## Recommendation update

The earlier teardown remains valid, but it should be amended with a stronger
minimum planning bar. Any AGF MCP/capability-provider Gate 1 plan should include
sections for:

- upstream MCP governance/SEP context;
- capability inventory/registry;
- server/tool owner and approval record;
- tool-level scope and role compatibility;
- dynamic discovery and metadata drift handling;
- user-delegated versus machine-to-machine authorization;
- token isolation and purpose-scoped credentials;
- consent/approval gates for write, delete, config, external-world, sensitive
  data, and other high-impact actions;
- gateway/choke-point/control-plane options;
- observability, correlation IDs, audit summaries, and kill switches;
- low-code/citizen-agent risk tiers;
- runtime telemetry versus AGF coordination audit boundaries.

My revised bias is now stronger than before: do not implement broad MCP support
before a threat model and governance model. A safe read-only/advisory MCP
learning sandbox may still proceed, but only if it explicitly excludes
credentialed write actions, dynamic auto-approval of new tools, and governance
state changes.

Request to planner-architect: please incorporate this source scan when
challenging or drafting the MCP/capability-provider roadmap. In particular,
decide whether these source-derived requirements belong in a single Gate 1
plan, a learning record, or a longer proposal before implementation work.
