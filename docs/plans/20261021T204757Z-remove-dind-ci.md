# Plan: remove Docker-in-Docker (DinD) from CI

## Decision requested

Approve a two-part plan to eliminate `dind` from `.gitlab-ci.yml`: (1)
an immediate, low-risk fix for four jobs mistagged onto the `dind`
runner pool despite needing no privileged Docker at all, and (2) a
bounded feasibility spike testing whether the two remaining genuinely
DinD-dependent jobs (Windows cross-compilation) can also move to
rootless Podman, extending issue #109's Phase B evidence to the one
target it deferred.

This is a Gate 1 plan only. It does not authorize implementation before
governor-reviewer approval, and Part 2's migration step (if the spike
passes) requires its own Gate 2 exact-head pipeline evidence before
merge, per the acceptance matrix below.

## Trigger and context

MR !3096's pipeline got stuck today: `rust:tooling:oci-pull-test` and
`agov:oci:mr-build-scan` sat `pending` for 28+ minutes because the only
online runner carrying the `dind` tag had stopped checking in with
GitLab (`contacted_at` 43+ minutes stale despite reporting `online`).
Investigating why these two particular jobs were even routed to that
pool surfaced that **4 of the 6 `dind`-tagged jobs in `.gitlab-ci.yml`
don't use the privileged DinD service at all**.

There is already an approved, phased Gate 1 plan for DinD removal:
`docs/plans/20260825T132059Z-issue109-runner-fleet-phasing.md` (issue
#109). Its state:

- **Phase B** (rootless-Podman feasibility for the Linux `cross build`
  targets) is done and merged —
  `docs/reviews/issue109-phase-b-feasibility.md` proved
  `CROSS_CONTAINER_ENGINE=podman`/`CROSS_REMOTE=0` builds
  `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl`
  successfully (one finding: per-target `CARGO_TARGET_DIR` isolation
  needed to avoid cross-image glibc symbol conflicts across sequential
  target builds).
- **Phase C** (Proxmox runner fleet, trust classes) and **Phase D**
  (the actual `.gitlab-ci.yml` migration) remain **unauthorized** —
  Phase C still needs an independent human infosec review per governor
  decision `20260826T111710Z-governor-reviewer-2jq3.md` before its own
  Gate 1 can be approved.
- Separately, since that plan was written, **mandatory Linux release
  packaging already migrated off `cross`/DinD entirely** via native
  musl toolchain compilation (`CHANGELOG.md`, v2.9.0-era entry:
  "mandatory Linux release packaging uses native musl tooling instead
  of Docker-in-Docker"). `.rust-tooling-package`'s mandatory path
  (`.gitlab-ci.yml:1500-1524`) now runs plain `cargo build --release
  --target "$target"` directly — no container engine at all.

**This plan does not replace or contradict issue #109.** Part 1 is
outside its subject entirely (pure mistagging, not a DinD-architecture
decision). Part 2 extends Phase B's exact bounded-environment method to
the one target (Windows) Phase B explicitly deferred as optional. If
Part 2's spike passes, this plan proposes that as sufficient grounds to
retire `dind` project-wide without ever needing issue #109's heavier
Phase C/D Proxmox buildout — the governor decides whether to formally
close out or leave dormant the remainder of issue #109's phase
structure.

## Part 1 — Fix the mistagged podman jobs (low risk, immediate)

Re-tag these four jobs from `tags: [dind]` to `tags: [podman, linux,
amd64]` (the pool `.gitlab-ci.yml`'s `default:` block already routes
everything else to, which currently has two online runners vs. the
dind pool's one dead one):

- `release:verify`
- `agov:oci:mr-build-scan`
- `rust:tooling:oci-pull-test`
- `agov:oci:release`

No `services:`, `script:`, or `variables:` changes — none of these jobs
declare a DinD service today, and their logic is untouched.

Also correct the stale comment at `.gitlab-ci.yml:81-83` ("The six jobs
that require nested containers override it locally with the dedicated
`dind` tag") to state the accurate count and name the two real
consumers.

## Part 2 — Windows-under-podman feasibility spike, then migrate or decide

**Feasibility spike**, same bounded method and evidence contract as
`docs/reviews/issue109-phase-b-feasibility.md`: in a disposable local
rootless-Podman environment (no new account, no paid resource, no
protected CI variable, no runner registration — identical stop
conditions to Phase B), attempt:

```sh
CROSS_CONTAINER_ENGINE=podman CROSS_REMOTE=0 \
cross build --release --target x86_64-pc-windows-gnu -p agov -p agov-mcp
```

Record the result in `docs/reviews/issue109-phase-b2-windows-feasibility.md`,
with the same rigor Phase B used: exact tool/image versions and
digests, exact command sequence, pass/fail with artifact checksums,
resource/time observations, and (if it fails) the complete failure log.

**If PASS**, migrate `.rust-tooling-windows-package` and
`rust:tooling:build:windows:preview` with the **full** scope below —
**correction (advisory review `1a72`, finding 2, accepted):** the
original plan listed only `services:`/`variables:`/`tags:` and named
`CARGO_TARGET_DIR` isolation, but omitted job runtime setup and
output-path consumers that the same migration must also change:

- Remove `services: [docker:dind]` and the `DOCKER_HOST`/
  `DOCKER_DRIVER`/`DOCKER_TLS_CERTDIR` variables; add
  `CROSS_CONTAINER_ENGINE: podman` and `CROSS_REMOTE: "0"`; re-tag both
  jobs to `[podman, linux, amd64]`.
- **Job runtime setup:** both jobs' `before_script` currently runs
  `apt-get install -y -qq docker.io` (the Docker *client* binary) to
  give `cross` something to talk to. This must change to install
  `podman` instead (the podman-pool runner's host engine is external to
  the job container; `cross` still needs an in-job CLI to invoke it via
  `CROSS_CONTAINER_ENGINE=podman`). Verify which exact package provides
  a working `podman` CLI against the job's base image (`rust:1.97.1`)
  and pin it the same way `docker.io` is pinned today.
- **Nested-container execution preflight:** before relying on the
  engine substitution in CI, confirm (not merely assume from the local
  Phase B/Phase B2 experiment) that the podman-pool runner actually
  permits nested container execution inside a job container — the
  local feasibility spikes run directly on a rootless-Podman host, not
  inside this project's own CI job container, which is one more layer
  of nesting the local experiment does not exercise.
- **Build-directory isolation, matching every consumer, not just the
  build step:** `.rust-tooling-package`'s packaging script reads
  `target/${target}/release/agov`/`agov-mcp` directly for both the
  staging/archive step and `verify-tooling-provenance.sh`, and the
  standalone `rust:tooling:build:windows:preview` job's `artifacts:`
  block hard-codes `tooling/rust/target/x86_64-pc-windows-gnu/release/
  agov.exe`/`agov-mcp.exe`. If `CARGO_TARGET_DIR` is overridden for
  cache-boundary isolation (per Phase B's finding), either (a) point
  every one of these consumers at the overridden directory, or (b)
  isolate only *during* the build and copy/move outputs back to the
  conventional `target/` path before staging/artifact collection runs.
  Name the exact chosen approach in the implementation MR; "isolate
  `CARGO_TARGET_DIR`" alone, as originally written, is incomplete and
  will silently break packaging or artifact collection.
- Required Gate 2 evidence is **both actual Windows CI jobs passing at
  the exact implementation head** (`rust:tooling:preview:windows-
  package` and `rust:tooling:build:windows:preview`, both `when:
  manual`), not merely a successful local host experiment — the
  feasibility record establishes the engine substitution is plausible;
  it does not substitute for the real CI jobs actually passing.
- At that point `dind` has zero remaining consumers in
  `.gitlab-ci.yml`. Recommend, as a follow-up outside this plan's
  scope (a GitLab project-settings action, not a repo change),
  deregistering the dead `dind`-tagged runner (id `55975189`, already
  `stale`/`paused`) from the project.

**If FAIL:** document the failure with the same rigor Phase B gave its
aarch64 surprise, and stop. The fallback choice — a scoped privileged
runner for just these two jobs, a native Windows runner, or dropping
Windows packaging — is a separate future governor decision, not
resolved by this plan.

## Governance classification

  `agov:oci:release` and `release:verify` are named explicitly in
  `agf/rules/always/high-risk-operations-rule.md` ("the `release:*`
  and `agov:oci:release` CI jobs"). This plan is the required
  stop-and-plan step before editing them.
- `.gitlab-ci.yml` is not a named trigger path in
  `agf/rules/always/downstream-impact-rule.md`; this is an internal CI
  change with no adopter-facing contract. **Adopter docs parity: not
  applicable.**
- **Correction (advisory review `20261021T210510Z-improvement-
  propeller-1a72`, finding 1, accepted):** `agov:oci:mr-build-scan`
  **and `agov:oci:release`** are gate mechanics under
  `agf/rules/always/gate-self-test-rule.md` — both call
  `agov-oci-image.sh`'s shared `scan_with_ref()` (the comment at
  `agov-oci-image.sh:401-404` states explicitly: "the MR-stage gate and
  the tag-stage gate must be the identical Trivy invocation"), which
  runs the pinned Trivy image with `--severity HIGH,CRITICAL
  --exit-code 1` and no `allow_failure` override — a preventive check
  blocking images with known HIGH/CRITICAL vulnerabilities, not merely
  named "validator." The original "none of the six jobs are gate
  mechanics" claim was wrong for these two. Re-tagging either still
  requires `gate-self-test-rule.md`'s negative test, demonstrated
  **after** the move: scan a deliberately HIGH/CRITICAL-vulnerable test
  image through the re-tagged job running on the podman pool and show
  it still exits non-zero and blocks, exactly as it does today on the
  dind pool. The other two Part 1 jobs (`release:verify`,
  `rust:tooling:oci-pull-test`) remain non-gate build/release jobs.
- `agov plan collision-check` reports a plan-vs-plan `affected_paths`
  overlap against `docs/plans/20260914T130217Z-row6-s4-issue123-
  collision-check-blocking-promotion.md` (both list `.gitlab-ci.yml`).
  That plan is about `collision-check`'s own gate mechanics (Rust
  validator, registry, tests) — a different subject with no actual
  content conflict against this plan's job-tag/service changes.
  Acknowledged via `depends_on` rather than narrowing either plan's
  `affected_paths`.

2. **Part 1**: on its own branch/MR, `agov:oci:mr-build-scan` and

   (e.g. an old unpatched base image) through `agov:oci:mr-build-scan`

   exercised by an MR pipeline; `agov:oci:release`'s own negative-test
   evidence is therefore satisfied by the identical shared
   `scan_with_ref()` call path already demonstrated via
   `agov:oci:mr-build-scan`'s negative test (same function, same
   severities, same exit code, per the script's own comment that the
   two invocations must be identical) — **not** independently
   re-demonstrated on a real tag pipeline, which would require
   deliberately publishing a vulnerable release image. State this
   substitution explicitly in the implementation MR so a reviewer can
   judge whether it is sufficient. **Known residual verification gap**
   (separate from the gate-self-test evidence): `release:verify`'s
   first real confirmation is still the next actual release tag,
   mitigated by the diff being purely mechanical (`tags:` only, no
   script/logic change) and by watching that tag's pipeline closely.

   migrating, an exact-head MR pipeline with both Windows jobs manually
   triggered (`when: manual`, their existing rule) and green is
   required before Gate 2.

## Risks

- Part 1 risk is minimal — these jobs are already podman-only; the
  change is pure routing. **Correction (advisory review `1a72`,
  finding 3, accepted):** if `agov:oci:release`'s next tag-pipeline run
  shows resource pressure on the podman pool, this job is one of the
  two named explicitly in `high-risk-operations-rule.md`'s "Release,
  tag, and publication mechanics" — its own STRICT classification
  above already rules out a fast-track fix for it. The original risk
  text contradicted the plan's own classification by calling a revert
  of this exact job "a fast-track fix"; removed. Any correction to this
  job's routing follows the same Gate 1 plan + governor-reviewer
  approval path as this plan itself, not a fast-track waiver.
- Part 2's Windows build may fail for reasons unrelated to engine
  choice (the MinGW cross image may assume real Docker-specific
  features). A FAIL is a valid, useful result — not a plan failure —
  and routes to the separate governor decision named in "If FAIL"
  above.

## Rollback

**Correction (advisory review `1a72`, finding 3, accepted):** the
original rollback section treated reverting `tags:` back to `dind` as
sufficient recovery for all four Part 1 jobs. It is not: the GitLab
project runner API confirms the project's `dind`-tagged runner (id
`55975189`) is `stale`/`paused` — the same dead pool that caused
today's MR !3096 incident. Reverting `tags:` to `dind` routes these
jobs back to a runner that is not currently executing jobs; it does
not restore service by itself.

**Part 1 rollback, stated accurately:** `git revert` restores the
previous `tags:` lines (same reversibility as before), but this
operationally leaves `release:verify`, `agov:oci:mr-build-scan`,
`rust:tooling:oci-pull-test`, and `agov:oci:release` **blocked** until
either (a) the `dind`-tagged runner is confirmed back online
(re-verify via the GitLab runner API before relying on a revert as a
recovery step), or (b) the revert is paired with routing those jobs to
a different, confirmed-live runner instead of back to `dind`. Do not
treat "reverted the diff" as "restored service" without that live
check.

**Part 2 rollback (if shipped then reverted):** `git revert` restores
`services: [docker:dind]`/the Docker variables/the `dind` tag on the
two Windows jobs — these still require a live `dind`-tagged runner to
actually execute, subject to the same caveat as Part 1's rollback
above.

`docker:dind` stays available as a runner/tag indefinitely unless the
dead runner is explicitly deregistered — that deregistration is
deferred to a human follow-up action outside this plan's scope, done
only after Part 2 confirms `dind` has zero remaining consumers.
