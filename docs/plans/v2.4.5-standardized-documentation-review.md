# Plan: v2.4.5 standardized multi-LLM documentation review

## Parent plan

This is the "separate Gate 1 plan for a standardized review run" required by
`docs/plans/v2.4.5-next-unplanned-release-assessment.md`'s "Required
review-evidence workstream" section, and by delivery handoff
`20260726T160225Z-planner-architect-45qq` (task 3). It does not redefine
v2.4.5's release identity or content lock; the parent plan remains
authoritative for sequencing, scope, and exclusions.

## Trigger

The parent plan's required v2.4.5 outcome is an auditable, current-state
critical review of the published documentation using a shared protocol
across multiple LLM perspectives. Historical model assessments (Lumo, Claude
Code, Grok, ChatGPT, GitHub Copilot, Cursor, OpenAI Web, Codex, GPT-5.6 Sol
High) exist but were performed at different times, against different
snapshots, and with different scopes and prompts — they are useful
provenance, not evidence that the current implementation was critically
reviewed. This plan defines the frozen protocol so a fresh, comparable,
provenance-complete review can run once, against one pinned baseline.

## Baseline

- **Tag:** `v2.4.4`
- **Merge commit:** `103930dbcdb9127cea65f1ca387ef13ed3ee7c10`
- **Release page:**
  <https://gitlab.com/janipaijanen/agents-govern-framework/-/releases/v2.4.4>
- **Normative reviewed source:** the immutable tagged tree,
  <https://gitlab.com/janipaijanen/agents-govern-framework/-/tree/v2.4.4/agf/docs/site/docs>.
  Reviewers read from that pinned ref (or a docs site rebuilt from that exact
  tag), not the live, mutable GitLab Pages root — `.gitlab-ci.yml` rebuilds
  Pages from later `main` changes, so the live site cannot itself serve as a
  frozen snapshot. Live Pages output may be used only as corroborating
  rendered evidence (e.g. confirming a page renders as the tagged markdown
  describes), never as the normative source of the reviewed text.

If v2.4.4 is superseded by a later release before this review executes, the
Gate 1 approval must be re-confirmed against the new baseline before
execution begins — do not silently substitute a newer tag.

## Target pages

Evaluator-facing and adopter-facing documentation under
`agf/docs/site/docs/` at the pinned tag, at minimum:

- Homepage / framework map
- Adoption decision path (evaluate.md, applicability-catalog.md,
  ai-evaluation-dossier.md)
- Installation and first-governed-change path (install-and-layouts.md,
  first-governed-change.md, tooling-and-tokens.md, mcp-server.md)
- Roles and gates (roles-and-gates.md or equivalent)
- Evidence and maturity vocabulary (maturity-vocabulary.md)
- Day-to-day / cold-start guidance (day-to-day.md,
  run-agf-in-real-situations.md, coord-graph-index.md)
- Upgrade and exit paths (upgrade-from-v1.md, exit-and-decommission.md)
- Tooling conformance reference (tooling-conformance.md)

The exact page list is fixed once this plan clears Gate 1 — no reviewer may
substitute a different page set mid-review.

## Shared review packet

Every reviewer receives, verbatim, the same:

- page list (above), in the site's actual navigation order (per
  `agf/docs/build/mkdocs.yml` at the pinned tag);
- target-audience statement per page (director/manager, employee,
  business-IT/administrator, developer, or AI assistant — per
  `documentation-audience-rule.md`);
- question set:
  1. Is required background (terms, gates, maturity levels) defined before
     first use in the reader's likely path through the nav order?
  2. Does page ordering match the decision a reader at this point actually
     needs to make (e.g. exit/migration decisions surfaced before deep
     mechanics)?
  3. Are claims about capability, evidence, or comparison to other tools
     verifiable per `implementation-honesty-rule.md` and
     `verifiable-claims-rule.md`?
  4. Are there missing, thin, or duplicated sections for this page's stated
     audience?
  5. Would a new adopter matching this audience be able to complete the
     page's implied task without external help?
- severity vocabulary: **critical** (blocks adoption or is factually false),
  **moderate** (meaningfully confuses or slows a first-time reader),
  **minor** (polish, thin section, would improve but doesn't block);
- required evidence fields per finding: page, section/heading, exact quoted
  text or line reference, severity, one-sentence defect statement, suggested
  fix (optional).

Reviewers submit an independent first pass before seeing any other
reviewer's findings. No reviewer may be shown another reviewer's output
before submitting their own.

## Minimum panel and independence labeling

- **Claude** (this assistant's own review pass).
- **Codex** and **GPT-5.6 Sol High** as two distinct review units — one
  assistant surface (Codex) and one model/interface (GPT-5.6 Sol High) are
  not interchangeable and must not be counted as a single reviewer.
- At least **two** externally supplied independent model perspectives
  selected from: Gemini, Grok, Cursor, GitHub Copilot, Lumo, or another
  named system.

Each actual review unit is enumerated separately with its own product,
interface, model, and session/exposure fields. Record the exact model
identifier when the provider exposes it; otherwise record the product,
date, interface, and the identifier limitation explicitly (do not omit the
field silently). Do not list a model as a reviewer unless its output is
actually captured. A compound label (e.g. "Codex / GPT-5.6") must not
double-count one captured output as two reviewers.

## Per-review provenance (required fields)

For every review unit's submission, record:

- reviewer/product name
- exact model identifier, or the stated limitation if the provider does not
  expose one
- UTC date of the review
- reviewed SHA/tag and URL (must be `v2.4.4` /
  `103930dbcdb9127cea65f1ca387ef13ed3ee7c10` for all reviewers)
- the complete prompt/protocol text sent (verbatim, including the shared
  review packet above)
- the unedited response
- normalized findings extracted from that response, each tagged with the
  evidence fields above

## External web-LLM prompt packet

For reviewers without direct repository/tool access (a "web-only" LLM
session), the copy-paste packet consists of:

1. A one-paragraph AGF background statement: what AGF is, that it is a
   documentation set for a self-governing multi-agent development
   framework, and that the reviewer is being asked to critically assess it
   as a prospective adopter or reviewer would, not to praise or summarize it.
2. The pinned tagged-tree URL (`v2.4.4/agf/docs/site/docs`) and instruction
   to read pages in the fixed nav order above.
3. The shared question set and severity vocabulary verbatim, above.
4. An explicit instruction: "Do not fabricate section names, quotes, or
   page contents you have not actually read. If you cannot access a linked
   page, say so rather than inferring its content."
5. The required output shape: one finding per row, columns matching the
   required evidence fields above.

The packet must be assembled once this plan clears Gate 1, stored as a
fixture (e.g. `docs/reviews/v2.4.5-review-packet.md`), and reused verbatim
for every external reviewer — not re-typed per session, which would
reintroduce exactly the protocol drift this plan exists to prevent.

## Synthesis procedure

1. Collect all review-unit submissions with full provenance.
2. Deduplicate findings that describe the same underlying defect across
   reviewers, but do not convert vote count into truth — a finding raised
   by one reviewer and missed by four others is not thereby false, and a
   finding raised by all five is not thereby proven without independent
   fact-check.
3. Separate findings into four categories: (a) factual defects (verifiably
   true or false against the pinned source), (b) usability/ordering
   judgments (subjective but actionable), (c) roadmap or scope-expansion
   proposals (out of scope for a documentation patch), (d) claims requiring
   human or empirical evidence this review cannot supply (e.g. "adopters
   find this confusing" without adopter data).
4. Route category (a) findings through fact-checker verification against
   the exact pinned tree before they may be cited as fact in any synthesis
   document.
5. Route the evidence-strength and independence-labeling correctness of the
   whole package through academic-peer-reviewer before it is treated as
   publishable.
6. Route the final package and proposed remediation dispositions through
   contribution-auditor.
7. Produce one synthesis document listing: corroborated findings (2+
   independent review units, with reviewer count and identities), single-
   reviewer findings (flagged as such, not discarded), and explicitly
   excluded categories (b)-(d) items routed elsewhere per the parent plan's
   scope-routing rules.

## Retention, copyright, and privacy boundaries

- Prompts sent to external, non-project-controlled LLM providers MUST follow
  `external-anonymization-rule.md`: codename-only across the codebase
  boundary if the project's real identity is not already intentionally
  public. (This project currently publishes under its real name on a public
  GitLab instance; if that remains true at execution time, this constraint
  is satisfied by the project's own public visibility and does not require
  additional redaction — record that determination explicitly in the
  synthesis document rather than assuming it silently.)
- Raw external-reviewer responses are retained as committed fixtures under
  `docs/reviews/` with their full provenance fields, not discarded after
  synthesis — a future auditor must be able to trace any synthesis claim
  back to the unedited response it came from.
- No PII, credentials, or secrets may appear in any submitted prompt or
  returned response committed to the repository. Screen before commit per
  `security-hardening-rule.md`.
- External-provider terms of service regarding submitted content (training
  use, retention) are the responsibility of whoever executes each review
  session with that provider; this plan does not itself authorize accepting
  any specific provider's terms — that remains a human decision at
  execution time.

## Explicit exclusions

- This plan does not execute any review itself — execution requires Gate 1
  approval first.
- This plan does not authorize contacting or purchasing access to external
  model providers. Human-supplied outputs may be incorporated only with the
  full provenance fields above.
- This plan does not predetermine findings or their remediation.
- Findings that would change schemas, roles, validators, authority, CI
  enforcement, or adopter contracts are routed to v2.5.0, per the parent
  plan, not remediated under this documentation-patch workstream.

## Gate requests

- **Gate 1:** governor-reviewer approves or blocks this review protocol
  (baseline, target pages, panel composition, provenance fields, synthesis
  procedure, retention boundary) before any review execution begins.
- **Gate 2:** applies to the exact synthesis-package MR and to each
  fact-checked remediation MR that results from it, not to this plan file.
