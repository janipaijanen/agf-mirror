# Plan: AGF v2.4.1 — accessibility and prose hardening

## Decision and release character

Prepare v2.4.1 as a governed **patch** release addressing three related,
previously-scoped defects, per issue #56 (milestone `v2.4.1`, Level 1
Planned candidate) and canonical handoff `4hbk`
(`20260723T060151Z-contribution-auditor-4hbk`):

1. **#51** — every public-documentation figure must have preceding prose
   that carries the figure's essential meaning independently.
2. **#55** — the five public-site Mermaid diagrams must not rely on
   shrink-to-fit as their only narrow-width presentation, and must have a
   recorded screen-reader-oriented semantic evaluation. This is the
   deferred v2.4.0 obligation from governor decision `5stq` (Decision 1).
3. **#56** itself — this plan document, satisfying "one Gate 1 plan
   covering #51/#55/#56" with contribution-auditor and infosec-sentinel
   statuses attached.

This is corrective work on already-shipped public surfaces — improving
existing prose and improving existing presentation of already-intended
information. It does not add a capability, schema field, role, tool, API
surface, or adopter-facing contract. See "Patch-version justification"
below for the explicit boundary check issue #56's contribution-auditor
comment required.

## Scope 1 — #51: explanatory prose before every figure

`agf/docs/site/ai-evaluation-dossier.md` (in `nav`). Both are corrected

Sum: 22. Verification command (anchored to line-start Markdown image
syntax, which naturally excludes `reference/figures.md`'s own inline
instructional example `` `![Alt text](figures/name.svg)` `` — that
example is prose describing the embed syntax inside a sentence, not a
line-start embed, so this pattern does not depend on its line number
and stays correct as prose is added around real embeds):

    rg -n '^!\[[^]]*\]\([^)]*\.(png|jpe?g|svg|gif)\)' agf/docs/site \
      --glob '*.md' --glob '!content-plan.md'

Five files repeat across pages (`gate-pipeline.svg` ×5,
`adoption-exit-flow.svg` ×4, `coordination-channel.svg` ×3,
`learning-loop.svg` ×3, plus two ×2 repeats). Per the issue's planning
boundary, each embed gets its **own** page-specific introduction
reflecting that page's context and argument — not one boilerplate
paragraph copy-pasted across occurrences, and not identical wording
between a page's narrative use of a figure and the same figure's
reference-gallery entry in `figures.md`. A reviewer must be able to
tell, from the prose alone and without the page name, which embed
instance they are reading.

### Requirement per embed

Before each of the 22 embeds:

- State why the figure is present at that point in that specific page's
  argument.
- State what relationship, sequence, comparison, or conclusion it
  communicates.
- State the key point the reader should retain.
- No content-free framing sentences ("the figure below shows the
  process").
- Existing captions, legends, cross-references, and alt text are
  **reviewed for sufficiency, not merely accuracy** (corrects `ahnk`
  BLOCK 3): each is checked for whether it provides an adequate
  accessible name/description on its own, not just whether it is
  factually correct. Preserve metadata found adequate; correct metadata
  found inadequate (missing accessible name, misleading, or redundant
  with the new prose to the point of confusion). The added prose remains
  the primary equivalent explanation; unchanged metadata is not itself
  evidence of quality — it is evidence only after this sufficiency
  review.

### Acceptance evidence (#51)

- Closed inventory table above, reconfirmed unchanged at implementation
  Gate 2 (re-run the exact verification command above against the exact
  reviewed SHA).
- Per-embed review recording page, figure, and a one-line confirmation
  that the introduction states a substantive takeaway (not a rubber-stamp
  checklist — an actual reviewer read).
- Confirmation that essential meaning is available without perceiving the
  image (read the prose alone, in page order, and confirm no information
  gap).
- Per-embed sufficiency finding for captions/legends/cross-references/alt
  text: adequate-preserved or inadequate-corrected, not a blanket
  "unchanged" claim.
- Strict MkDocs build (`mkdocs build --strict` or project equivalent) and
  link/anchor check pass at the exact implementation SHA.
- No claim of any change to v2.4.0's shipped content — this is entirely
  new commits on a v2.4.1 branch.

## Scope 2 — #55: Mermaid mobile presentation and screen-reader semantics

### Inventory (closed, five diagrams — reconciled against MR !429's exact reviewed SHA)

A page-scoped sweep of `agf/docs/site/docs/` alone found only four
diagram fences. The fifth lives on the **site landing page**,
`agf/docs/site/index.md`, which sits outside `docs/` and was missed by a
sweep scoped too narrowly. Reconciled directly against MR !429's exact
Gate-2-approved SHA (`ea56abcbe24cc918bb7eaf1e96b9858fb8f636fc`,
`git grep -c '```mermaid'`), confirming this is the same set `5stq`'s
"five Mermaid diagrams" refers to — nothing has been removed or
consolidated since.

| Page | Mermaid diagram count | Diagram type(s) |
|---|---|---|
| `index.md` (site landing page) | 1 | flowchart (responsibility-palette `classDef`) |
| `concepts/coordination-protocol.md` | 1 | `sequenceDiagram` (documented default-colour exception, `5stq` Decision 2) |
| `concepts/position.md` | 2 | flowchart (responsibility-palette `classDef`) |
| `start/framework-map.md` | 1 | flowchart (responsibility-palette `classDef`) |

Total: **5 diagrams**, matching issue #55's stated count exactly. This
inventory is closed; implementation should re-run the same reconciled
sweep (`docs/` **and** `index.md`) at its own exact SHA as an acceptance
check, not re-derive it from scratch.

### Requirement

For each of the five diagrams:

- Evaluate at a representative narrow/mobile width (390px, matching
  `5stq`'s stated failure width) without relying on shrink-to-fit as the
  only presentation strategy. Candidate remedies: horizontal scroll
  container, simplified mobile-specific diagram variant, or a responsive
  Mermaid renderer configuration — chosen per-diagram based on what
  actually fixes legibility, not applied uniformly without checking.
- Perform a named, repeatable semantic evaluation (corrects `ahnk` BLOCK
  3's "vague screen-reader-oriented review"), in two parts:
  1. **DOM/accessibility-tree inspection** — inspect the rendered SVG's
     accessibility-tree exposure (browser DevTools Accessibility panel or
     equivalent) for each diagram: is there an accessible name, is the
     content exposed as decorative/presentational or as meaningful
     content, are individual nodes/labels reachable.
  2. **At least one actual screen-reader/browser smoke test** across the
     shared rendering pattern (not per-diagram if the pattern is
     genuinely shared) — record the specific tool, version, and OS used
     (e.g. NVDA + Firefox on a named Windows build, or VoiceOver +
     Safari on a named macOS version), and the concrete observed
     behaviour, not just pass/fail.
  - Per diagram, confirm whether equivalent prose in the surrounding page
    carries the diagram's essential relationships — record this finding
    per diagram, not as one blanket page-level statement.
  - Explicitly record method limitations (single AT/browser combination
    tested, not exhaustive AT coverage) — no claim of universal
    assistive-technology conformance from one smoke test.
- Preserve the `coordination-protocol.md` sequence diagram's documented
  default-colour exception (`5stq` Decision 2) unless a separately
  approved design change revisits it — out of scope for this plan to
  re-litigate.
- Apply the shared responsibility palette (`classDef`/`class`) to any
  flowchart diagram not already covered by an existing documented
  exception.

### Acceptance evidence (#55)

- Closed five-diagram inventory (see reconciled inventory above)
  reconfirmed unchanged at implementation Gate 2.
- Desktop-width and 390px-width rendered evidence per diagram (screenshot
  or equivalent captured evidence, per
  `workflow/visible-artifact-verification-rule`'s visual-acceptance
  gate — this is exactly the class of change that rule targets).
- Keyboard reachability, zoom/reflow behavior, and the named DOM/AT-tree
  plus screen-reader smoke-test evidence per diagram, per the method
  above (tool/version/OS recorded, limitations disclosed).
- Confirmation that essential meaning remains available without
  perceiving the diagram (same standard as #51's figure prose).
- Strict site build and link/anchor validation pass.
- Explicit statement: no claim of formal WCAG conformance is made without
  the full evidence set above — partial evidence is reported as partial,
  per `implementation-honesty-rule`'s maturity-level discipline.

## Patch-version justification

Per contribution-auditor's `4hbk`/issue-#56-comment requirement: this
release is scoped as v2.4.1 (patch), not v2.4.2 or a minor bump, because
every change in scope 1 and scope 2:

- corrects a defect in already-shipped, already-intended information
  (the figures and diagrams already exist and already carry a claimed
  meaning; this plan makes that meaning actually available to readers who
  cannot or do not perceive the image);
- adds no new schema field, role, tool, CLI flag, MCP surface, or
  adopter-facing contract;
- touches only prose, existing-site CSS/templates, and presentation
  configuration (Markdown text, Mermaid theme/config, MkDocs
  CSS/template adjustments already present in the site build) under
  `agf/docs/site/` — the full site tree, correcting the prior draft's
  narrower `agf/docs/site/docs/`-only claim (`ahnk` WARN 1) — not code,
  schemas, or release-artifact contracts.

**If inventory work (the discrepancy in scope 2, or unexpected findings
during scope 1's per-page review) surfaces anything requiring a schema,
role, tooling/API, or adopter-contract change, that finding must be
split out of v2.4.1 into its own separately-scoped issue and plan** — it
does not silently expand this patch's scope. This is a standing
implementation constraint on this plan, not merely a note.

## Plan/implementation split (resolved per `ahnk`)

**One Gate 1 plan (this document) and one implementation MR**, with two
logical commits and two separately reported evidence sections — one for
#51, one for #55 — not separate branches. Reasoning, per contribution-
auditor's `ahnk`: the two scopes overlap on the Mermaid-diagram pages
(`index.md`, `coordination-protocol.md`, `position.md`,
`framework-map.md`), since the explanatory prose #51 requires is also
part of #55's equivalent-text remediation for those diagrams. Separate
branches would duplicate page review, risk merge conflicts on the same
files, and add pipeline cost without improving governor review quality.
Release packaging (`release/v2.4.1` branch, VERSION bump, CHANGELOG)
remains a later step, after the integrated docs implementation MR passes
Gate 2 — not bundled into the same MR as the content changes.
