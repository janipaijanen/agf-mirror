# Plan: v2.4.0 Workstream A — consumer-facing release asset names

## Intent

Rename the public filenames of Rust tooling release archives (and their
checksum/provenance sidecars) away from the raw Rust cross-compilation
target triple to a short, non-technical platform slug. Framework source
archives (`agf-X.Y.Z.tar.gz`/`.zip`) are unaffected — they carry no
target-triple component today and are out of scope.

- Scope/compatibility analysis: `20260721T134012Z-coder-tester-q8ej`.
- Binding naming decision: `20260721T134559Z-governor-reviewer-er5h`,
  acknowledged by `20260721T134801Z-coder-tester-rsr4`.

  BLOCK findings, all resolved in this revision).

## Binding decisions (from `er5h`, restated for implementers)

1. Public slugs: `x86_64-unknown-linux-musl` → `linux-x86_64`;
   `aarch64-unknown-linux-musl` → `linux-aarch64`;
   `x86_64-pc-windows-gnu` → `windows-x86_64`.
2. Real Rust target triples are retained everywhere else: `cross build
   --target`, `.cargo/config.toml`, and the provenance record's
   `target_platform` field. Only the *public filename* changes.
3. No old-name aliases are published. No confirmed external dependent on
   the current naming exists (Phase 0, per
   `agf/rules/workflow/deprecation-policy-rule.md`).
4. Disclosed as `Changed (breaking)` in `agf/CHANGELOG.md`, with the
   Phase 0 no-deprecation-cycle rationale stated in one sentence.
5. Historical artifacts, tags, changelog entries, plans, and coordination
   records keep their original names — nothing already published is
   renamed or rewritten.

## Why this is a small, mechanical change (not a second artifact identity)

Workstream B already separated the two identities the umbrella plan
worried about conflating:

- `target_platform` (provenance record field) — the real Rust triple,
  set via `--target-platform "$target"` in `.gitlab-ci.yml`, already
  independent of the archive's filename.
- `artifact_filename` (provenance record field) — a plain string derived
  from whatever path is passed to `--artifact`, with no built-in
  assumption that it matches the triple.

Renaming the archive on disk and passing the new name to `--artifact`
changes `artifact_filename` correctly with zero Rust code changes and no
schema migration: `provenance-record file` already treats the artifact
path as an opaque input. This plan is CI-script and documentation scope
only.

## Affected files (exhaustive)

### `.gitlab-ci.yml`

- `.rust-tooling-package` (shared job template used by both
  `rust:tooling:preview` and `rust:tooling:release`):
  - Add a triple→slug mapping (shell `case` statement) evaluated once per
    loop iteration and once for the Windows block.
  - `archive="agov-${VERSION}-${target}.tar.gz"` →
    `archive="agov-${VERSION}-${slug}.tar.gz"` (and `.zip` for Windows).
  - The staging directory name embedded *inside* the archive
    (`agov-${VERSION}-${target}/`) also changes to
    `agov-${VERSION}-${slug}/`, so an extracted archive's top-level
    directory matches its own filename.
  - `--target-platform "$target"` is unchanged (real triple).
  - `--artifact "../../dist/${archive}"` — unchanged in form, now
    resolves to the new filename automatically since `$archive` changed.
  - `README.txt`'s `Target: %s` line keeps the real triple (technical
    detail for someone who opens the archive), not the public slug —
    explicit choice, see "Open design decisions" below.
- `release:create` job: two `tar -xzf
  "dist/agov-${VERSION}-x86_64-unknown-linux-musl.tar.gz"` /
  `AGOV_BIN="$staging/agov-${VERSION}-x86_64-unknown-linux-musl/agov"`
  self-extraction blocks (used to obtain a host-native `agov` binary for
  provenance validation) → `dist/agov-${VERSION}-linux-x86_64.tar.gz` /
  `$staging/agov-${VERSION}-linux-x86_64/agov`.
- `release:verify` job (added by the Workstream B merge): same
  self-extraction pattern, same two-line change.

### `tooling/rust/scripts/agov-oci-image.sh`

Real functional dependency, not documentation-only — corrected per
`jm6q` BLOCK 2 (a prior revision of this plan wrongly excluded this
file as unaffected). Two call sites construct the tooling archive path
directly from `AGOV_TARGET`, defaulting to the real triple:

- Line 63-64 (`build`) and line 135-136 (`provenance`):
  `target=${AGOV_TARGET:-x86_64-unknown-linux-musl}`;
  `archive="dist/agov-${AGOV_VERSION}-${target}.tar.gz"`.
- Line 26 (usage docstring): names the same path in prose.

After this workstream, the public archive at that path no longer
exists under the triple-based name — only `agov-${AGOV_VERSION}-
linux-x86_64.tar.gz` is published for the default (and currently only
CI-invoked) `x86_64-unknown-linux-musl` target. Fix: add the same
triple→slug mapping used in `.gitlab-ci.yml` to derive the *archive
filename* from `AGOV_TARGET`, while leaving `AGOV_TARGET` itself (the
real triple, used for `cross build --target` elsewhere in this
project's build config) untouched — same separation of concerns as
`.rust-tooling-package`: internal build target vs. public artifact
name. Update the usage docstring's example path to match. No other
`AGOV_TARGET` consumer in this script needs to change — `AGOV_TARGET`
continues to select the real Rust cross-compilation target for the
*staged binary*, per its existing documented purpose.

### `tooling/rust/scripts/release-assets.sh`

- `expected()`: the 9 hardcoded tooling filenames (3 targets × archive +
  `.sha256` + `-provenance.json`) change to the slug-based names.
  Framework archive entries (`agf-*`) are unaffected.
- `selftest`: the negative-test fixture name
  (`agov-${test_version}-aarch64-unknown-linux-musl.tar.gz-provenance.json`)
  changes to `agov-${test_version}-linux-aarch64.tar.gz-provenance.json`
  so the self-test still exercises a name matching the real policy.
- `list()`'s glob patterns (`agov-*.tar.gz`, `agov-*.zip`, etc.) are
  already name-agnostic — confirmed in `q8ej`, no change needed.

### `agf/docs/site/reference/release-artifacts.md`

- The artifacts table (`dist/agov-X.Y.Z-x86_64-unknown-linux-musl.tar.gz`
  etc.) updates to the new slugs.
- Every CLI usage example in this file that names a real-looking archive
  (`self-report-check`, `post-publication-check` context, `dist
  provenance-record file`) updates its example filename to the new
  scheme, so copy-pasted examples match what a real release actually
  produces.

## Open design decisions (for Gate 1 approval, not implementer discretion)

1. **README.txt inside the archive: real triple or public slug for the
   `Target:` line?** Recommendation: keep the real triple. The README is
   read by someone who already has the archive open on disk and may want
   to cross-reference the exact Rust target (e.g. for a bug report); the
   public slug is already the filename they see everywhere else.

(CHANGELOG entry timing was the second open decision in a prior
revision; resolved, not open — see "Affected files" → `agf/CHANGELOG.md`
above, per `jm6q` BLOCK 3.)

## Acceptance tests

1. `release-assets.sh list`/`expected`/`verify` operate correctly against
   a `dist/` directory built with the new names (positive case).
2. `release-assets.sh verify` fails, naming the specific missing file,
   when a slug-named file is absent (negative case — already the
   pattern `selftest` exercises, just re-pointed at the new names).
3. A real `rust:tooling:preview` (or `release`) CI run produces exactly
   the new-slug filenames — `agov-X.Y.Z-linux-x86_64.tar.gz`,
   `agov-X.Y.Z-linux-aarch64.tar.gz`, `agov-X.Y.Z-windows-x86_64.zip` —
   and no `x86_64-unknown-linux-musl`/`aarch64-unknown-linux-musl`/
   `x86_64-pc-windows-gnu` string appears in any *filename* under `dist/`
   (a grep-based negative assertion, distinct from the provenance
   record's `target_platform` field value, which legitimately still
   contains the triple).
4. `agov dist validate-provenance dist/*-provenance.json --artifact-dir
   dist` (Workstream B's own validator) passes against the renamed
   artifacts — proves `artifact_filename`/`sha256`/checksum-sidecar
   agreement survives the rename with zero Rust code changes, as
   predicted above.
5. `release-artifacts.md`'s CLI examples are copy-paste consistent with
   what step 3 actually produces (checked by hand at Gate 2 review, not
   an automated test — this file has no existing doc-example-vs-reality
   CI check and adding one is out of scope for this plan).
6. `agov-oci-image.sh build` and `agov-oci-image.sh provenance`, run
   locally (or in the `rust:oci:*` CI job) against a `dist/` directory
   populated with the new slug-named archive, locate and extract
   `dist/agov-X.Y.Z-linux-x86_64.tar.gz` correctly with `AGOV_TARGET`
   left at its real-triple default — proves the archive-path derivation
   fix (per `jm6q` BLOCK 2) actually resolves the new filename rather
   than only updating the usage docstring.

## Rollback

Revert the `.gitlab-ci.yml`/`release-assets.sh`/`release-artifacts.md`
commit(s). No data migration, no schema change, no published artifact is
affected — this only changes what the *next* release's filenames look
like. Safe to revert at any point before a tag is pushed with the new
names; per `immutable-tags-rule.md`, a tag already pushed with new names
cannot be un-published, only superseded by a later version.

## Risks

- **Low.** Mechanical rename confined to CI scripting and documentation.
  The main risk is an incomplete rename (a missed reference to the old
  triple-based filename somewhere in `.gitlab-ci.yml` or
  `release-assets.sh`) producing a broken release upload or a 404'd
  documentation example — mitigated by acceptance test 3's grep-based
  negative assertion and by `release-assets.sh verify`'s existing
  fail-fast behavior in `release:create`.
