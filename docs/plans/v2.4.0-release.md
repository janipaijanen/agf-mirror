# Plan: AGF v2.4.0

## Decision and release character

Prepare v2.4.0 as a governed minor release after v2.3.1. The governor has
expanded the target beyond patch-release documentation corrections to include:

1. clearer consumer-facing release-asset filenames;
2. a coherent documentation figure and responsibility-colour system;
3. one unified release-provenance contract and validator; and
4. privacy-bounded attribution of direct CLI versus MCP-mediated telemetry.

The aggregate is not a patch. Public asset names change, a release-evidence
contract is introduced, telemetry records gain transport attribution, and the
documentation visual system changes across the public site. The release is
therefore v2.4.0.

This umbrella plan controls scope and sequencing. It does **not** authorize a
single broad implementation branch. Every workstream below requires its own
approved Gate 1 child plan, implementation MR, validation evidence, and Gate 2
decision before the release branch may include it.

## Release scope

### Prerequisite corrections

Before the release base freezes:

- merge the adoption-time and exit-effort evidence correction already prepared
  after v2.3.1;
- merge the rule-loading evidence correction from MR !328 after its description,
  formatting, pipeline, and Gate 2 findings are resolved;
- merge the persistent `AGF / <page>` header and `AGF — <page>` browser-title
  correction from MR !330 after responsive visual review and Gate 2 approval;
- resolve MR !329 by recording that these post-v2.3.1 corrections belong in
  the v2.4.0 changelog rather than inventing an unrelated patch release.

These corrections are part of v2.4.0 but do not replace the four governed
workstreams below.

### Workstream A — consumer-facing release asset names

Create a child plan and implementation MR that:

- maps canonical Rust targets to these public slugs:
  - `x86_64-unknown-linux-musl` → `linux-x86_64`;
  - `aarch64-unknown-linux-musl` → `linux-aarch64`;
  - `x86_64-pc-windows-gnu` → `windows-x86_64`;
- renames each tooling archive and its checksum/provenance sidecars using the
  public slug while retaining exact Rust triples in build configuration and
  provenance metadata;
- publishes no old-name aliases, as already decided;
- updates CI expected-asset lists, release links, tests, install/reference
  documentation, examples, and provenance subjects together;
- adds a `Changed (breaking)` changelog entry, a before/after migration table,
  and the Phase 0 rationale: zero known external production dependents on the
  filename surface, so no deprecation cycle is used;
- proves the exact public asset set and a missing/incorrect-name negative case.

Historical release assets, tags, changelog entries, plans, and coordination
records retain their original names.

### Workstream B — unified release-provenance contract

Create a child plan and implementation MR for a shared, versioned contract
covering framework source archives, platform tooling archives, and OCI evidence.
The smallest common required core is:

- schema version, product, artifact kind, version, source commit, tag, build
  timestamp, implementation, and packaging;
- public artifact filename, byte size, and SHA-256 linkage;
- artifact-specific target-platform fields for binaries and digest/label
  agreement for OCI images;
- executable self-report agreement for version, commit, and clean build state;
- public/reproducible pipeline and job identifiers only when available.

Required implementation outcomes:

- a JSON Schema under `agf/schemas/`;
- deterministic local validation during packaging;
- post-publication validation of artifacts downloaded from the public release
  surface—not merely the CI workspace;
- compatible handling of pre-v2.4 provenance records with an explicit support
  rule rather than silently treating them as v2.4 records;
- negative tests for missing, mismatched, dangling, duplicated, malformed, and
  checksum-inconsistent evidence;
- adopter and release-operator documentation using the same contract language.

The contract uses a closed allowlist. It MUST NOT persist client, assistant,
model-session, conversation, correlation, request, user, or host identifiers;
prompts or responses; raw MCP/JSON-RPC envelopes; home paths; secrets; or raw
environment dumps.

Security review additionally requires provenance generation to reject unknown
metadata keys at the trust boundary. Public CI/job identifiers may be included
only as individually named fields whose values already belong to the public
release pipeline; an implementation must not serialize an environment-derived
map and then attempt to redact it afterward.

### Workstream C — MCP versus direct CLI telemetry

Create a child plan only after planner-architect and contribution-auditor
critically answer the questions in `20260721T074427Z-coder-tester-j36g`.
The implementation MR must:

- distinguish `transport: cli` from `transport: mcp` using a small controlled
  vocabulary;
- attribute the trusted local adapter (`agov-mcp`) without recording the MCP
  client or session;
- decide explicitly whether fixed tool-name attribution provides enough value
  to retain;
- keep new fields optional so existing JSONL readers remain compatible;
- define spoof-resistance expectations for any child-process marker;
- review/redact command arguments under the existing telemetry policy rather
  than expanding collection merely because MCP is involved;
- update telemetry documentation and reports so comparisons do not conflate
  transport with implementation;
- add negative tests proving prohibited identifiers, request envelopes,
  prompts, responses, and arbitrary metadata cannot reach disk.

This is transport attribution, not request tracing. No client or session IDs
may be written to disk.

The child plan must not claim that a local environment marker cryptographically
proves MCP origin: another local process may reproduce it. Treat the field as
trusted-adapter attribution for measurement, not as security/audit identity.
The plan must also enumerate which existing argument values can contain paths,
record identifiers, or free-form text and define redaction or omission before
adding transport fields.

### Workstream D — figure system and responsibility-labelled text blocks

Create a child plan and implementation MRs small enough for visual review. The
workstream covers all current public documentation figures and their source
files, including inline Mermaid diagrams embedded directly in Markdown, plus
the academic SVG/PDF figures where the same defects occur.

Required outcomes:

- replace every legend swatch that describes an oval, diamond, box, or line
  with the actual visual shape or line style;
- remove literal shape-parenthetical workarounds such as “oval shape” beside a
  rectangle;
- make every meaningful colour, fill, border, arrow, and line style consistent
  with an embedded legend or direct labelling;
- use one semantic responsibility palette across the documentation:
  orange for human decisions, blue for AI-executed work, green for automated
  checks/validated outcomes, outlined neutral for shared concepts, and grey for
  reference/deferred content;
- never rely on colour alone; labels, shapes, borders, and accessible text must
  preserve the meaning in greyscale and for colour-vision deficiencies;
- remove the full-size “AGF in a Nutshell” flyer from the documentation overview
  reading flow, retaining it as a clearly labelled standalone/downloadable
  orientation artifact with an optional restrained thumbnail;
- remove or replace the documentation-audience map when native page components
  communicate the responsibility categories more clearly;
- add restrained responsibility-labelled text blocks for Human decision, AI
  action, Automated check, Shared concept, and Reference; use them only where
  responsibility changes or ambiguity is likely, not around ordinary prose;
- keep source DOT/templates, generated site SVG/PNG copies, and academic
  SVG/PDF outputs synchronized;
- test representative desktop, narrow/mobile, light, dark, print/greyscale, and
  screen-reader semantics;
- keep figures within documented page-width/readability constraints or provide
  an intentional accessible scroll treatment.

The child plan must inventory every figure and record a per-figure disposition:
retain, redesign, relocate, replace with native HTML/table, or retire.

Workstream D remains a release blocker even if its closed inventory is larger
than expected. Schedule pressure is not authority to reduce the inventory or
silently defer individual figures. Moving all or part of this workstream to a
later release requires an explicit governor decision and an amended umbrella
plan before release freeze.

## Advisory consultation findings

### Contribution-auditor

- **BLOCK** — one implementation MR for all four workstreams would make scope,
  evidence, and rollback unreviewable. Resolved by mandatory child plans and
  independent Gate 2 MRs.
- **BLOCK** — asset naming and provenance cannot be designed independently:
  provenance subjects must use the new public filenames while target fields
  retain canonical triples. Resolved by implementing the generic provenance
  core first and integrating the final filename mapping in Workstream A.
- **WARN** — a visual “consistency” pass could become unbounded subjective
  redesign. Resolved by requiring a closed inventory and per-figure
  retain/redesign/relocate/replace/retire disposition.
- **WARN** — Phase 0 permits no-cycle breakage but does not permit euphemistic or
  undisclosed breakage. Resolved by the mandatory `Changed (breaking)` entry,
  migration table, and zero-known-dependent rationale.

### Infosec-sentinel

- **BLOCK** — provenance or telemetry must not accept or persist arbitrary
  metadata maps. Resolved by closed schemas/allowlists and unknown-key negative
  tests.
- **BLOCK** — no client, session, request, prompt, response, raw envelope,
  environment dump, home path, secret, or host fingerprint may reach disk.
  Resolved as an explicit contract plus prohibited-field fixtures.
- **WARN** — command arguments can already contain paths or free-form values;
  adding MCP attribution must not imply existing argument logging is safe.
  The telemetry child plan must inventory and redact/omit sensitive argument
  classes.
- **WARN** — a child environment marker is spoofable by another local process.
  Documentation must present transport as measurement attribution, not security
  provenance.

## Dependency and merge sequence

1. Resolve and merge prerequisite documentation MRs !328, !329, and !330.
2. Approve the four child plans; advisory findings must be resolved before the
   affected implementation begins.
3. Implement Workstream B's provenance schema/core before finalizing
   Workstream A, because renamed assets must emit the new provenance shape.
4. Implement Workstream A against that contract and prove exact public names.
5. Workstreams C and D may proceed independently in separate worktrees/MRs.
6. Freeze scope only after all four workstreams have passed Gate 2 and merged.
7. Create a dedicated `release/v2.4.0` branch from the frozen main commit.
8. On the release branch, change release truth surfaces only: versions,
   changelogs, release metadata, generated release inventories, and the release
   coordination trail. Do not implement deferred product work there.
9. Merge the release MR after Gate 2, tag its merge commit, and verify every
   public surface before recording completion.

## Release-wide acceptance criteria

- `agf/VERSION`, Rust workspace/package versions, lockfile versions, assistant
  loader markers, both changelogs, Pages release information, archives, binary
  self-report, OCI labels, Git tag, and GitLab Release agree on `2.4.0` and the
  release merge commit where applicable.
- Both changelogs contain a complete v2.4.0 entry. The breaking asset rename is
  under `Changed (breaking)` with migration guidance and Phase 0 rationale.
- `agov validate adopter-docs` passes and every adopter-relevant workstream's
  Gate 2 handoff records adopter-doc parity.
- Rust tests, clippy/parity checks, strict MkDocs build, figure regeneration
  checks, schema/validator tests, telemetry privacy negative tests, packaging
  tests, and host release preflight pass.
- Every produced archive passes explicit path-hygiene inspection: no `.git`,
  `__pycache__`, `.pyc`, local `tmp`, absolute, or traversal paths.
- The GitLab Release exposes the exact required archive, checksum, and
  provenance set under the new public asset names.
- Every checksum verifies after downloading from the public Release surface.
- Every provenance record validates against the intended contract version and
  agrees with its downloaded artifact, tag, version, and commit.
- Linux x86_64 and OCI runtime smoke tests pass; architecture/platform outputs
  are verified to the supported extent recorded in the release handoff.
- Pages displays the v2.4.0 content and persistent AGF page identity after the
  release pipeline completes.
- A completion record enumerates tag object, peeled commit, pipelines, Release,
  exact assets, checksums, provenance, OCI digest, runtime checks, Pages, and
  both changelog surfaces.

## Explicitly out of scope

- MR !117 in its current form; its academic snapshot remains stale and requires
  a separately governed refresh before it can enter any release.
- Old-name compatibility aliases for release assets.
- Client/session/request tracing or open-ended telemetry metadata.
- Signing, Sigstore, SBOM expansion, or a transparency-log service unless a
  child plan demonstrates they are strictly required by the approved
  provenance contract and the governor expands scope.
- Historical rewriting of immutable tags, assets, coordination records, plans,
  learning records, or changelog entries.
- Unrelated product features discovered while these workstreams are active.

## Stop conditions

- A child implementation starts before its plan is Gate 1-approved.
- A public filename changes without migration guidance and the Phase 0
  breaking-change disclosure.
- Provenance or telemetry accepts an open metadata map or persists a prohibited
  identity/session/request field.
- Generated figures are edited without changing their source or source and
  generated copies diverge.
- A legend describes a visual shape or line using a different sample.
- Release scope changes after freeze without an updated plan and explicit
  governor decision.
- Any version, tag, changelog, archive, provenance, binary, OCI, Pages, or
  Release-page truth surface disagrees at publication time.
