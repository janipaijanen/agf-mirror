# Plan: v2.4.0 Workstream C — MCP vs. direct CLI telemetry attribution

## Intent

Add low-cardinality transport attribution (`transport: cli|mcp`, `adapter`,
`tool`) to the existing `agov-core::roi` ROI/token-savings JSONL log, so
usage reports can distinguish MCP-mediated invocations from direct CLI
invocations, per `docs/reference/tooling-token-roi.md`'s existing purpose.
This is workflow-measurement attribution, not request tracing or security
identity — no client, session, correlation, or request IDs, no prompts, no
responses, no raw JSON-RPC envelopes.

While implementing this, close a real, pre-existing privacy gap that
`skg4`'s critical review found and `n8s6` confirmed: `agov-core::roi`
already writes the complete raw `std::env::args()` vector to disk for
*every* invocation today, direct CLI and MCP-mediated alike, with no
redaction, allowlist, or filtering anywhere in the pipeline. Per `n8s6`,
this fix must apply uniformly to both transports — Workstream C may not
ship an MCP-only redaction layer bolted onto an unaudited CLI baseline.

## Mandatory boundaries (from `n8s6` — binding on this plan)

1. **Never serialize raw marker values.** `agov-mcp` may set child-process
   environment markers, but `agov` must parse exact known values and emit
   fixed constants/enums (`transport: "mcp"`, `adapter: "agov-mcp"`, a tool
   name from a compiled allowlist). Unknown, malformed, or contradictory
   values are omitted or mapped to a documented safe default — never
   persisted verbatim. A local caller can still spoof a *valid* marker;
   document this explicitly rather than adding disproportionate
   pseudo-authentication (no HMAC signing, no PID-tree verification).
2. **Raw `args` cannot remain on disk**, for either transport. Default-deny
   all argument values; do not attempt a blacklist of known-sensitive
   strings. The audit must cover every ROI-recording call site's option
   values and positional arguments, decide the compatibility contract for
   historical readers, and document any semantic change to `args`.

## Redaction policy for `args` (resolves boundary 2; tightened per `hr4p` BLOCK 3)

Every current `agov-core::roi::record_tool_output` call site (~20, all in
`tooling/rust/crates/agov/src/main.rs`) passes the CLI's own argument
vector, sourced from `std::env::args()` at line 437. These arguments mix
closed-vocabulary tokens (subcommand names: `coord`, `validate`, `dist`;
enum flags: `--kind review`, `--id-format ulid`) with flags that carry
free-form or identifying text (`--topic`, `--task`, `--dir`, `--id`,
`--from`, `--to`, `--ref`, `--artifact`, `--model`, `--check`, `--paths`,
`--files`, `--since`, `--format` where format arguments may include
arbitrary paths).

Policy: **default-deny**, over the exact token stream `redact_args`
receives, with these binding rules for every edge case in that stream —
not left to the implementer to invent:

- `argv[0]` (the program name/path) is never included in the input to
  `redact_args` — callers pass only the subcommand-and-flags slice, as
  they already do today (`args` at `main.rs:437` is sliced after the
  program name before any call site is reached).
- **`--flag=value`** is split into flag and value before the allowlist
  check runs; the flag name is matched exactly as if it were
  `--flag value`, and the value is redacted or retained under the same
  rule as the space-separated form. No separate equals-form allowlist.
- **The `--` delimiter**: everything after a bare `--` is treated as
  positional values, not flags, and redacted under the positional-value
  rule below — never matched against the flag-name allowlist.
- **Positional (non-flag) values**: redacted by default, exactly like a
  non-allowlisted flag's value. The one exception is exact allowlisted
  command-path tokens (subcommand/sub-subcommand names like `coord`,
  `validate`) — those retain their position and text because they are
  closed vocabulary, not free text, even though they are positional.
- **Repeated flags** (e.g. multiple `--ref`): each occurrence is
  evaluated independently under the same flag-name/value rule; repetition
  does not change a flag's allowlist status.
- **Short aliases** (e.g. `-k` for `--kind`, if any exist): the allowlist
  is keyed by canonical flag identity, not literal string — an alias
  must resolve to the same allowlist entry as its long form, or it is
  treated as unrecognized (redacted) if no such mapping exists.
- **A flag with a missing value** (e.g. `--kind` as the last token, no
  value follows): the flag name is retained per the ordinary flag-name
  rule; there is no value to redact, and `redact_args` must not panic or
  shift subsequent tokens.
- **Unknown/unrecognized flags**: the flag name itself is retained
  (flag *names* are never secret — they're the CLI's own compiled
  surface), but its value is always redacted, exactly like a known
  free-form flag. Unknown does not mean "pass through raw."

A small starter allowlist of flags whose *values* are closed vocabulary
(e.g. `--kind`, `--id-format`) may retain their value; every other flag's
value is replaced with a fixed redaction marker (e.g. `"[redacted]"`)
rather than dropped, so record shape and argument-count-based diagnostics
stay stable for historical-reader compatibility.

The full per-flag allowlist/redact table (which specific flags get
closed-vocabulary value retention beyond the starter set above) is an
implementation deliverable built from the exhaustive flag audit `skg4`
recommended — the Gate 1 commitment binding at this plan's level is the
complete edge-case algorithm above, not the final per-flag table.

## Marker parsing contract (resolves boundary 1; tightened per `hr4p` BLOCK 3)

Transport/adapter/tool resolution is **one coherent tuple decision**, not
three independently-parsed fields:

- **No markers present** → direct CLI. Emit `transport: "cli"` explicitly
  (see below); `adapter` and `tool` remain absent.
- **An exact allowlisted MCP tuple present** (all required markers set to
  values in the compiled allowlist) → emit all three MCP fields:
  `transport: "mcp"`, `adapter: "agov-mcp"`, and the matched tool name.
- **Any partial, malformed, or contradictory tuple** (e.g. the transport
  marker says `mcp` but the tool marker is missing or unrecognized; a
  marker is present but not in the allowlist; markers name a tuple that
  doesn't correspond to any real `agov-mcp` tool) → emit **none** of the
  three attribution fields (fall back to the direct-CLI shape,
  `transport: "cli"`) and never persist the source values that produced
  the rejection. A malformed MCP call must not silently masquerade as a
  clean "cli" record's absence-of-markers case, so `resolve_transport`'s
  internal rejection path is unit-tested separately from the true
  no-markers case even though both produce the same output shape.

## Acceptance tests

1. `RoiRecord` with `transport`/`adapter`/`tool` all `None` serializes
   identically (byte-for-byte JSON shape minus new keys) to the current
   record shape — proves additive compatibility for old readers.
2. A fixture JSONL line missing `transport`/`adapter`/`tool` still
   summarizes correctly via `summarize()`/`load_records()` — explicit
   regression test per `skg4` Q5, matching `feature-regression-guard-rule`.
3. Negative test: setting `AGOV_MCP_TRANSPORT` to an unrecognized or
   malformed value results in `transport: None` (or the documented safe
   default), never the raw string, in the serialized record.
4. Negative test: an env value containing a client/session/request
   identifier, a raw JSON-RPC-shaped string, prompt/response text, a home
   path, or a secret-shaped string is never present in the serialized
   record — proves the closed-parse boundary, not just the happy path.
5. Negative test: for a call with free-form flag values (e.g.
   `--topic "some sensitive-looking text"`), the serialized `args` field
   contains the redaction marker, not the original value.
6. Positive test: a call using only allowlisted closed-vocabulary flags
   (e.g. `coord validate --kind review`) retains those tokens/values
   unredacted — proves the allowlist doesn't over-redact diagnostic value
   away.
7. Direct CLI invocation (no MCP env markers set) records
   `transport: "cli"` (per open decision 2) with no `adapter`/`tool`.
8. `agov-mcp`-mediated invocation (integration test spawning `agov` with
   the markers `run_agov` sets) records `transport: "mcp"`,
   `adapter: "agov-mcp"`, and a tool name drawn from the same allowlist
   `tool_cli_args` uses.
9. `AGOV_TOKEN_ROI=off` / logging-disabled behavior is unchanged (no
   regression to the existing disable switch at `roi.rs:31-34`).
10. `try_append`'s existing write pattern (as it stands at implementation
    time — `writeln!`-based today, or `write_all`-based if governor option
    (b) above lands first) is unchanged by this plan — no new write call,
    no new file handle pattern introduced. Per governor option (a) (this
    plan's recommendation), add a follow-up obligation: once !363 merges,
    re-run this test against the post-!363 `write_all` contract and
    confirm it still holds.

## Rollback

Revert the `RoiRecord` field additions, the `redact_args`/
`resolve_transport` functions, and the `agov-mcp` env-marker-setting
change. Historical JSONL is unaffected either way — the format change is
purely additive/redactive on new writes.

## Risks

- **Over-redaction reduces diagnostic value.** The default-deny policy may
  redact flag values that would have been useful for workflow diagnosis
  and weren't actually sensitive. Mitigation: the allowlist can be
  extended in a follow-up once real usage shows which flags are safe and
  useful; expanding an allowlist is a low-risk additive change, unlike
  starting permissive and later needing to retroactively restrict.
- **Scope creep into full request tracing.** The three fields are
  workflow-measurement attribution only. Any future proposal to add
  session/request/client identity is explicitly out of scope and requires
  its own plan and its own privacy review — not a quiet extension of this
  one.
