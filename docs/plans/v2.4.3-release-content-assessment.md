## Version-number collision

MR !483's plan hard-codes `v2-4-3-doc-quality-and-ia-backlog` as its id and
`v2.4.3` in its filename and prose, but it has not yet cleared Gate 1 (its
own advisory_consultation front matter shows a fourth submission still under
active re-review as of this writing). The four fixes above (#64, #65 already
merged; #66, #30 Gate-2-ready) are independent of that backlog and much
further along.

**Proposal:** the four issue fixes ship as **v2.4.3**. MR !483's backlog plan
is renamed to **v2.4.4** (id, filename, and prose) before it receives Gate 1
approval — a cheap edit now, versus a stale version claim in an
already-approved plan later. This does not change MR !483's scope, only its
version-number binding, and is offered as a proposal for contribution-auditor
and the plan's own author to weigh in on, not a unilateral rename — the plan
file lives on MR !483's branch, not this one.

## Proposed v2.4.3 release sequencing

1. Governor clears Gate 2 for MR !515 (#66) and MR !463 (#30); both merge to
   `main`. (#64 and #65 are already merged — no further Gate 2 action needed
   for those two beyond what's already recorded.)
2. Add `CHANGELOG.md` entries for all four changes under `[Unreleased]` —
   currently empty despite two of the four already being on `main`.
3. Per `release-via-merge-request-rule.md`: cut `release-2.4.3` from `main`
   (all four fixes already merged at that point), bump `VERSION` and
   `CHANGELOG.md` only on the release branch, open the release MR, merge,
   tag `v2.4.3`, push the tag immediately per the rule's no-further-
   confirmation step.
4. MR !483's backlog plan (proposed rename to v2.4.4) continues its own Gate
   1 review independently and becomes the next release after v2.4.3, once
   approved and implemented.

## Acceptance evidence

- Contribution-auditor reviews this triage and the version-number proposal.
- If accepted: MR !483's plan file is updated to v2.4.4 naming by its own
  author/branch before Gate 1 approval.
- Once #66 and #30 clear Gate 2, `CHANGELOG.md`'s `[Unreleased]` section is
  populated and the `release-2.4.3` branch is cut per the standard workflow.

## Explicit exclusions

- This plan does not implement, merge, or tag anything itself.
- This plan does not reopen or re-litigate any already-approved Gate 1 or
  Gate 2 decision on #64, #65, #66, or #30.
- This plan does not act on the backlog or stale-issue items listed above
  beyond flagging them.

## Gate requests

- **Gate 1:** governor-reviewer approves or blocks this sequencing proposal.
- **Gate 2:** not applicable — this plan produces no code/doc diff of its
  own; its "implementation" is the release-cut sequence in step 3, which is
  itself governed by `release-via-merge-request-rule.md`, not a fresh Gate 2.
