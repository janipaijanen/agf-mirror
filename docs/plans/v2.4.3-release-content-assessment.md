issues are worth including in a release, and if release-content candidates
exist, plan the release(s). This plan is that assessment plus a proposed
sequencing, routed to contribution-auditor for review before any release
branch is cut.

### Integration evidence gap — #30 / MR !463

MR !463's branch is currently 124 commits behind its recorded base. Its
implementation pipeline passed at `323e065cee4603607b3b8dd115cda632edf0925d`,
but that SHA does not demonstrate integration with current `main`, and its
visible head is a later coordination-only commit. Per
`always/verifiable-claims-rule.md`, old green evidence at a stale SHA is not
a current integration result. **#30 is not called release-ready here.** It
becomes a candidate for this release only if, before the release branch is
cut: the branch is refreshed onto current `main`, the scoped Rust/validator
evidence is re-run and passes at the new exact head, and governor Gate 2
approves that exact SHA. If that has not happened when the release branch is
cut, #30 is deferred to whichever release follows — it is not blocking.

## Version numbering

The first draft of this plan proposed renaming MR !483's plan from v2.4.3 to
v2.4.4 to resolve a perceived collision with the three fixes above. That
proposal is withdrawn: MR !490
(`docs/plans/v2.4.4-stable-sha-procedural-trial.md`) already claims v2.4.4
for its own, unrelated stable-SHA procedural-trial content — a rename would
have moved the collision, not resolved it.

**Governor disposition (`20260725T090712Z-governor-reviewer-qg61`):** MR
!483's Gate 1 is approved at exact SHA `50f1bebb866514cbc4f2b99b933bd30de7b37c79`
and it explicitly retains the v2.4.3 identifier. This plan does not reserve
v2.4.3 for issues #64/#65/#66/#30 and does not propose moving MR !483 to
v2.4.4 — both directives from `qg61` are already satisfied by the withdrawal
above; this paragraph records that explicitly rather than leaving the
reconciliation implicit.

**No rename is proposed.** #64, #65, and #66 are already merged to `main`
ahead of MR !483's cut point; when a `release-2.4.3` branch is eventually cut
from `main` (after MR !483's Gate 1 and Gate 2 both clear), that branch
inherently contains all three merges already, whether or not MR !483's own
plan text discusses them. **v2.4.3 = "everything merged to `main` since
`v2.4.2`" at cut time**, not only the content of any single plan file. MR
!483's plan keeps its number because it already legitimately owns it and is
further along than a fresh rename would leave it. #30 joins v2.4.3 only if it
clears the integration-evidence gap above before the branch is cut; otherwise
it rolls to the release after next (v2.4.4 is already spoken for by MR !490).

## Proposed v2.4.3 release sequencing

1. MR !483's Gate 1 is already approved and merged (`b73ae2b`); its six
   frozen items are handed off to coder-tester (coordination-only MR !523,
   `status: ready`, unacknowledged as of this writing). Once coder-tester
   acknowledges and implements — on a branch based on `main` at or after
   `d60e059d0d277edf7462a0bfce1b530a113e8c68` per MR !483's own "Sequencing
   with MR !504 / MR !511" section — governor clears Gate 2 for that exact
   implementation SHA, and it merges
   to `main`.
2. If #30/MR !463 clears the integration-evidence gap above (refreshed onto
   current `main`, re-run scoped evidence, fresh governor Gate 2) before step
   3, it merges to `main` too. If not, it is left out of this release.
3. Per `release-via-merge-request-rule.md`: cut `release-2.4.3` from `main`
   (containing MR !483's merge, plus #30 if step 2 completed in time — #64,
   #65, and #66 are already present in `main` from their own merges). On the
   release branch only, bump `VERSION` and add the `CHANGELOG.md` entry
   covering every change since `v2.4.2` (#64, #65, #66, MR !483's items, and
   #30 if included). Open the release MR.
4. **Gate 2 applies to the exact release MR SHA** — the diff (VERSION bump +
   CHANGELOG entry), CI result, and any distribution-archive build must be
   reviewed and explicitly approved before merge, per
   `release-via-merge-request-rule.md`'s own checklist. This plan's "Gate 2:
   not applicable" framing in its first draft was wrong; corrected below.
5. After that MR merges: tag `v2.4.3` and push the tag immediately — the
   merged release MR is the authorization, no further confirmation step,
   per `release-via-merge-request-rule.md`.

## Acceptance evidence

- Contribution-auditor reviews this triage and the version-numbering
  resolution.
- `CHANGELOG.md`'s `[Unreleased]` section stays empty until the release
  branch itself carries the entry — no pre-branch changelog commit on `main`.
- The release MR's diff is reviewed and CI-green before merge (Gate 2, per
  step 4 above).

## Explicit exclusions

- This plan does not implement, merge, or tag anything itself.
- This plan does not reopen or re-litigate any already-approved Gate 1 or
  Gate 2 decision on #64, #65, #66, or MR !483.
- This plan does not declare #30/MR !463 release-ready; it states the exact
  evidence gap that would need to close first.
- This plan does not act on the backlog or stale-issue items listed above
  beyond flagging them.

## Gate requests

- **Gate 1:** governor-reviewer approves or blocks this sequencing proposal.
- **Gate 2:** applies to the exact `release-2.4.3` MR SHA once cut (step 4
  above), per `release-via-merge-request-rule.md` — not to this plan file,
  which produces no code/doc diff of its own.
