# v2.11 release scope and sequence

## Authoring provenance

Authored by a Claude session playing **planner-architect** under governor
directive "plan refined contents for next release" (2026-09-09). The
independent contribution audit MUST come from a non-author session.

## What this plan is, and is not

**It is:** a bounded IN / CANDIDATE / DEFER disposition of the post-v2.10
workstreams into v2.11, their ordering and dependencies, and the release
cut. It is derived from and must stay consistent with the governed roadmap
owner `docs/roadmap.md` (merged in queue-convergence B1) and the collision
disposition `ds4k`.

**It is not:** a re-approval of any workstream's own Gate 1 or Gate 2, a
version bump, a schema/validator/CI/rule change, or an implementation work
order. Each admitted workstream keeps its own Gate 1, exact-head reviews,
and binding Gate 2. This plan sets the scope boundary and sequence only.

## Ordering constraint, stated first

The **lifecycle/provenance freeze** is the spine of v2.11:

> issue #129 freeze-blocking compatibility slice → `qbka` Slice A
> (provenance-bound `superseded` schema + validator) → both (a) issue
> #122's coordination-record supersession provenance shape and (b)
> queue-convergence's plan-MR disposition cohort.

Nothing that depends on the frozen provenance contract may implement ahead
of `qbka` Slice A. The Improvement Propeller Stage 4 track (#131) is
**independent** of this freeze and may proceed in parallel.

## Release cut — delegated to a mandatory child plan

This scope plan **does not** contain an executable release-cut procedure
and **grants no tag, release, or publication authority**. Cutting v2.11
requires two things this plan does not supply:

1. **A child v2.11 release-publication plan** with its own Gate 1. It — not
   this plan — specifies completely: the exact metadata allowlist; the
   current-version inventory across every governed surface; source/target
   drift invalidation; retention of the preflighted local-only metadata
   commit as the MR head; runner/DinD readiness checks; the protected-tag
   policy checkpoints (below); and forward-only recovery after the tag is
   pushed. The child plan owns the `agov dist` / `agov release` command
   sequence with **actual verified job names**, not the release skill's
   stale `build-dist -> create-release` shorthand.
2. **A separate binding governor decision** authorizing the tag and
   publication, made *after* the v2.11 release-metadata MR has merged. A
   merged metadata MR is not itself tag/publication authorization
   (AGENTS.md; `release-via-merge-request-rule`).

### Constraints the child plan must carry

- **Release-cut precondition** — the two-part condition in "Pre-cut
  governor dispositions" above (all merge-based IN work merged at Gate 2
  **and** every non-merge acceptance condition — #131 genuine wake +
  Level-5 follow-up — complete).
- **Reversible preflight** — the `rg6k` amended sequence: allowlisted
  metadata as a disposable draft → all reversible validations → one
  unpublished local-only metadata commit → `agov release namespace-check
  --phase preflight` from that clean commit before any push.
- **Metadata MR contents** — `agf/VERSION` `2.10.0 → 2.11.0`; both
  changelogs (Improvement Propeller **activation** entry — `Changed`,
  adopters opt in per the rule Scope; the plan-lifecycle `superseded`
  schema entry; the coordination-protocol-semantics entries; queue-
  convergence ledger outcomes worth a line); `agf/agents/*.yaml`
  `framework_version` bumps; and the `docs/roadmap.md` +
  `agf/docs/site/roadmap.md` sequence-table sync (see "Roadmap-owner
  sync" below).
- **`release:namespace-check` (issue #120) is exercised as a
  *regression*, not a first run.** v2.10's release-metadata MR !2549
  already ran the gate successfully (pipeline `2829685860`, job
  `16368435839`), followed by tag pipeline `2829968146` — per `re48`.
  v2.11 is a subsequent regression exercise of the same
  `merge_request_event` + `agf/VERSION`-change job, not its debut.
- **Protected-tag policy checkpoints** — the exact `v2.11.0` protected-tag
  rule must exist and match **before** preflight, and be re-read
  immediately **before** the tag push; `agov release namespace-check`
  does not inspect protected-tag rules. Fail closed on a missing or
  mismatched rule.
- **Tag step** — after the separate governor authorization: create the
  annotated `v2.11.0` tag and push it immediately (one action; no
  intervening approval gate), then tag pipeline → GitLab Release +
  generic package + OCI → anonymous post-publication verification → a
  completion record.

`documentation-rule-projection-rule` scope is a plan that *introduces,
changes, or removes normative operating guidance in an adopter-facing

scope plan mutates no file: the normative owner of "what v2.11 contains"

## Risks and controls

- **Scope balloon.** The coordination cluster + `qbka` + #129 could each
  grow. Control: this plan admits *membership and sequence* only; each
  workstream's own Gate 1 bounds its size, and CANDIDATE items slip to
  v2.12 rather than expanding v2.11.
- **The #129 → `qbka` freeze dependency slips**, blocking #122 and the
  plan-MR cohort. Control: the #129 slice is deliberately the *smallest*
  freeze-blocking unit (per `6s5d`), not the full assessment.
- **Propeller Level 5 does not land in the window.** Control: #132 becomes
  a named v2.12 follow-up; the v2.11 changelog states Propeller as
  activated / Level-5-pending, never as fully deployed (`qkj2`).
- **`main`-churn during the v2.11 cut** (the `jprj` CP-B pattern). Control:
  the child release-publication plan authorizes **one bounded, explicitly
  scoped v2.11 target-hold** for the cut window (as `2brd` did manually
  for v2.10). This scope plan does **not** adopt CP-B's general
  coordination-hold mechanics — CP-B is CANDIDATE only, and any standing
  hold mechanism waits for CP-B's own Gate 1.
- **Author/reviewer collapse.** Control: non-author contribution audit;
  disclosed here and in the `advisory_consultation` row.

## Rollback

This is a scope plan. It creates no revertible artifact beyond itself. A
scope change (adding, removing, or reordering a workstream) is a governor
decision recorded in coordination, superseding the relevant row here.
