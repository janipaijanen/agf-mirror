# Plan: Workstream B — unified release-provenance contract

**Date:** 2026-07-21
**Parent:** `docs/plans/v2.4.0-release.md` (approved, Gate 1 decision
`20260721T195521Z-governor-reviewer-4ng5`)

## Trigger

The v2.4.0 umbrella plan requires Workstream B (provenance core) to merge
before Workstream A (asset renaming) can finalize, because renamed assets
must emit the new provenance shape. This is the first child Gate 1 plan
for that umbrella, per its own required sequencing.

Original scoping handoff:
`20260721T091004Z-coder-tester-sj5g` ("Future TODO: unified
release-provenance contract and validation").

## Current state (evidence, not assumption)

Verified against the actual code and docs, not the umbrella's summary
alone:

- **Framework source archive provenance**
  (`tooling/rust/crates/agov/src/dist.rs::write_provenance`) already emits
  `version`, `source_commit`, `tag`, `build_timestamp`,
  `pipeline_identity` (`pipeline_id`, `job_id`), `manifest_path`,
  `archive_filenames[]`, `checksums{}` (keyed by filename),
  `implementation`, `packaging`.
- **Rust tooling archive provenance**
  (per `agf/docs/site/reference/release-artifacts.md`) adds
  `target_platform`, `implementation: rust`, `packaging`, but — per
  `sj5g`'s original finding, reconfirmed here — **does not embed its own
  archive filename or checksum**, relying on an adjacent `.sha256` file
  and a filename convention instead of an in-record linkage.
- **OCI image provenance**
  (`tooling/rust/Containerfile.agov`) uses
  `org.opencontainers.image.{title,description,source,version,revision,licenses}`
  labels only — no JSON provenance record at all, and no schema-validated
  linkage between the label set and the other two surfaces.

Three surfaces, three different mechanisms, no shared schema, no single
validator that proves they agree with each other or with the artifacts
they describe.

## Scope

### In scope

- One JSON Schema under `agf/schemas/release-provenance.schema.json`
  (versioned: a `schema_version` field, not a bare filename version).
  Modeled as a **closed discriminated union keyed by `artifact_kind`**,
  not one flat shape — an OCI image is not inherently a
  filename/byte-count/SHA-256 tuple, and requiring file-linkage fields on
  it would force a meaningless value into every OCI record:
  - **Common required core (every kind):** `schema_version`, `product`,
    `artifact_kind`, `version`, `source_commit`, `tag`, `build_timestamp`,
    `implementation`, `packaging`.
  - **`artifact_kind: file`** (framework source archive, tooling archive):
    requires `artifact_filename`, `artifact_bytes`, `sha256` — closing the
    tooling-archive gap identified above — plus `target_platform` for
    tooling binaries specifically.
  - **`artifact_kind: oci-image`**: requires a canonical image reference
    (`registry/repository:tag`), the manifest digest, and required-label
    agreement (`org.opencontainers.image.{version,revision}` must match
    the record's `version`/`source_commit`). No `artifact_filename` field
    exists on this variant — it is not optional-and-empty, it is absent
    from the schema for this kind.
  - **Record cardinality: exactly one provenance record per published
    artifact.** The framework source archive currently emits one record
    covering both `.tar.gz` and `.zip` via aggregate `archive_filenames[]`
    /`checksums{}` arrays — this plan changes that to one record per file,
    matching tooling and OCI records, so every kind has an unambiguous
    single-filename or single-digest identity and the duplicate-filename
    negative test has a precise object set to check against.
  - **Executable self-report agreement:** for `artifact_kind: file`
    records whose artifact is itself an executable/archive containing one,
    the contract requires the packaged binary's own
    `--version`/`version --format json` output (`version`,
    `source_commit`, `dirty`) to match its provenance record at
    validation time — a validator rule, not just a schema shape.
  - **Build identity:** `pipeline_id`/`job_id` included only when the
    values already belong to the public, reproducible release pipeline
    (i.e., real `CI_PIPELINE_ID`/`CI_JOB_ID` values on a tag pipeline);
    `"unknown"`/`"untagged"` placeholders remain valid for local/dev
    builds, matching current `dist.rs` behavior.
- **OCI provenance publication location, concretely.** The OCI provenance
  JSON is published as a named GitLab Release asset (e.g.
  `agov-oci-provenance-<version>.json`), the same discovery mechanism
  already used for every file-artifact provenance record — not "alongside
  the image labels," which is not a publicly fetchable location on its
  own. The record's manifest digest is the linkage back to the registry
  image; a discovery/linkage test fetches the Release asset, reads the
  digest, and confirms it matches the actual pulled image's digest. No
  OCI referrers, signing, or SBOM mechanism is introduced to carry this —
  a Release asset is sufficient and consistent with the other two kinds.
- **Closed allowlist enforcement.** The schema uses
  `"additionalProperties": false` at every object level, including inside
  each `artifact_kind` variant. A provenance generator that tries to
  serialize an unrecognized key, or a `file`-only field on an `oci-image`
  record, fails schema validation rather than silently passing through.
- **Two validation lifecycles, kept separate:**
  1. **Build-time / local:** extend `agov dist validate` (or add
     `agov dist validate-provenance`, decided during implementation
     against actual CLI ergonomics) to validate a freshly generated
     record against the schema before packaging completes.
  2. **Post-publication:** a separate check that downloads the actual
     published artifact and provenance record from the public GitLab
     Release surface (file kinds) or pulls the actual image and reads its
     digest (OCI kind), and validates the record against both the schema
     and that real downloaded/pulled evidence — not the CI workspace
     copy. This is the check that would have caught a "provenance says X,
     published artifact is actually Y" class of defect.
  3. **Deployability of the validator itself.** The released `agov`
     binary must be able to run both lifecycles standalone, without a
     framework source checkout. `AGOV_SCHEMA_DIR` (today's mechanism) only
     resolves inside a foundry checkout and is not a packaged operator
     path. The schema is embedded into the `agov` binary at compile time
     (e.g. `include_str!` of the schema file), so a downloaded release
     binary can validate provenance with no other files present.
- **Backward compatibility is a contract decision, not an implementation
  detail.** Pre-v2.4 provenance records (missing `schema_version`,
  aggregate-shaped framework records, tooling records missing
  `artifact_filename`/`sha256`) are validated against a distinct, named
  `legacy` shape. The validator's result for a legacy-shaped record always
  reports an explicit `assurance_level: legacy` (or equivalent) — it MUST
  NOT ever report a legacy record as satisfying the `v2.4` contract, even
  if every field the legacy shape happens to have is individually valid.
- **Seven negative tests** proving the validator actually rejects: missing
  required core field; mismatched `sha256` vs. real artifact; dangling
  reference (provenance names a file that doesn't exist in the release);
  duplicated `artifact_filename` across records; malformed JSON; an
  unknown/extra top-level key or wrong-kind field (closed-allowlist
  enforcement); checksum format inconsistency (BSD `.sha256` file vs.
  record disagreement).
- **Documentation.** Update `agf/docs/site/reference/release-artifacts.md`
  to describe the unified contract in place of the current three-surface
  description, using the same field names the schema and validator use —
  no paraphrase drift between docs and schema.

### Out of scope (deferred to sibling workstreams or later)

- Workstream A's specific filename-slug mapping (`linux-x86_64`, etc.) —
  this plan defines the `artifact_filename` field's *shape*, not its
  final value; Workstream A supplies the value once this schema exists.
- Workstream C's telemetry transport-attribution fields — release
  provenance and operational telemetry are different data models with no
  shared schema, per this session's critical review of the umbrella plan.
- Signing, Sigstore, SBOM, or transparency-log integration — explicitly
  out of scope for the whole umbrella unless a future child plan
  demonstrates it's strictly required.
- Rewriting or reissuing provenance for already-published releases
  (v2.3.1 and earlier) — historical provenance records keep their
  original shape permanently.

## Security boundary (binding, not advisory)

The schema and every generator MUST NOT include: client, assistant,
model-session, conversation, correlation, or request identifiers; user or
host identifiers; prompts or responses; raw MCP/JSON-RPC envelopes; local
usernames or home paths; secrets or credentials; raw environment-variable
dumps. `additionalProperties: false` is the mechanical enforcement; this
line is the human-readable statement of what that enforcement is for.

## Affected files

| File | Change |
|---|---|
| `agf/schemas/release-provenance.schema.json` | New — the discriminated-union contract, embedded into the `agov` binary at compile time (e.g. `include_str!`) so a downloaded release binary validates without a source checkout |

| `docs/coordination/<gate2-handoff>.md` | Gate 2 handoff after implementation |

## Risks

| Risk | Mitigation |
|---|---|
| Schema drifts from the docs description | Doc update uses identical field names in the same commit as the schema |
| Pre-v2.4 records silently misreported as compliant | Explicit named legacy shape, never implicit upgrade |
| Post-publication validator only checks the CI workspace copy, missing "published artifact differs from what CI built" defects | Post-publication mode downloads from the actual public Release surface, not the pipeline's local `dist/` |
| Provenance generator serializes an environment map then redacts | Forbidden by design — closed allowlist means there is never an open map to redact from |
| OCI provenance JSON and existing OCI labels disagree | Validator checks label/JSON agreement, not just JSON internal validity |
| OCI provenance record published without a discoverable, testable location | Concrete location decided now (named GitLab Release asset, same discovery path as file-kind records), with a discovery/linkage test, not deferred to implementation |
| A released `agov` binary can't validate provenance without a framework checkout | Schema embedded into the binary at compile time; `AGOV_SCHEMA_DIR` is not the deployable path |
| File-kind and OCI-kind records ambiguous about which fields apply to which | Closed discriminated union by `artifact_kind`; each variant's `additionalProperties: false` rejects a field from the wrong kind |

## Rollback

Revert the schema, generator, and validator commits. No historical
provenance record is modified or reissued; the schema is additive to what
already ships.
