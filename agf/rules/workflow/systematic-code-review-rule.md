# Systematic Code Review Checklist
#
# Framework principle: Pre-commit quality gate
# See: framework.md — Pattern 5 (Cross-Cutting Review), ADOPTING.md Step 3

Run this checklist before proposing any commit. Every section. Every time.
A **BLOCK** item means: do not propose the commit until it is fixed.

---

### 1. Specification compliance
- [ ] Code does what was asked -- no more, no less
- [ ] No unasked-for changes to unrelated files
- [ ] Consistent with the plan file (if one was written)

### 2. Domain rules (**BLOCK if violated**)
- [ ] Migration files generated by the migration tool, not hand-written
- [ ] New models use the project's standard primary key type
- [ ] Meaningful views and edits use the designated audit log functions
- [ ] No SQL injection via string formatting -- use parameterised queries
- [ ] State-dependent write guards enforced where applicable (e.g. locked records, past periods)
- [ ] Business number arithmetic uses appropriate precision (not floating-point)
- [ ] Migration tool shows exactly one head (no branching)

### 3. Security and visibility (**BLOCK if violated**)
- [ ] No secrets, tokens, credentials, or API keys in code or comments
- [ ] Every new route checks permissions before data access
- [ ] User input validated through schema (or equivalent) before use
- [ ] Any new outbound HTTP call validated against SSRF (no arbitrary URLs)
- [ ] CSRF protection not disabled in any non-test config
- [ ] Tenant isolation code cross-checked against security tests

### 4. Tests and regression guard (**BLOCK if violated**)
- [ ] Every new behaviour has a test (unit or integration as appropriate)
- [ ] Tests assert meaningful outcomes, not just HTTP 200
- [ ] Test coverage has not been lowered
- [ ] Security-sensitive behaviour has a test in the security test directory
- [ ] No existing test deleted or weakened without a replacement that covers the new intended behaviour (see `feature-regression-guard-rule`)
- [ ] If modifying an untested feature: characterisation test written first to capture current behaviour before the change

### 5. Code quality
- [ ] No duplication of existing helpers (check existing utilities first)
- [ ] No N+1 query patterns (no DB query inside a loop over query results)
- [ ] Module docstring present or updated if public behaviour changed
- [ ] No catch-all exception handler that silently swallows a meaningful error
- [ ] User-initiated actions produce visible feedback: success confirmation, validation errors with field-level detail, or progress indication for operations >1s

### 6. Internationalisation and accessibility
- [ ] All new user-facing strings in templates use the i18n function
- [ ] New strings shown to users use the i18n translation system
- [ ] No new locale outside the approved set
- [ ] New interactive elements have accessible names (aria-label or visible text)
- [ ] New form fields have associated label elements
- [ ] Colour is not the sole means of conveying information

### 7. Documentation
- [ ] CHANGELOG updated if this is a user-visible change
- [ ] Plan file exists if change touched >1 module
- [ ] README updated if a build target, env var, or workflow changed

### 8. Commit hygiene
- [ ] No `Co-authored-by`, `Signed-off-by`, or AI-tool trailers in commit message
- [ ] Commit message describes the change, not the process or the tool used

---

## Final gate

**All BLOCK items clear?** -> Propose the commit.
**Any BLOCK item unresolved?** -> Fix it first, re-run the checklist.
