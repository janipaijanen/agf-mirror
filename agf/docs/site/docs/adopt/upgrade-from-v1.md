# Upgrading from v1 (agents-govern) to AGF v2

*Status: Released (v2.1 documentation). Audience: AI assistants carrying out
the v1-to-v2 migration under adopter review, plus humans supervising the
migration. After this page you have a step-by-step checklist that covers every
instruction surface that must be updated, not just the file copy.*

!!! note "What changed structurally"
    v1 placed framework files in `agents-govern/` (or a local copy) with numeric
    coordination sequence files and Elixir/Python `mix agov.*` commands.
    v2 places them in `agf/` with tooling-generated readable ID coordination files
    and the Rust `agov` binary.

## Before you start

This is a governed change. Open a branch and a plan or fast-track waiver before
touching any files.

The migration has two risk areas:

1. **Split-brain instruction surfaces.** After the file copy, every place that
   teaches agents or humans to use `agents-govern/`, numeric sequence files, or
   `mix agov.*` will silently route work through v1 patterns. These are the
   failures the checklist is designed to surface.
2. **Stale adopter learning records.** A learning record that validates as
   correct YAML may still carry v1 framework paths, retired role names, or
   workstation-local tool paths. This second category only surfaces under
   an explicit role review pass.

---

## Migration checklist

Work top to bottom. Do not mark a step done until you have verified it.

### 1. Retire old layout paths

- [ ] Remove or archive `agents-govern/` from the active layout.
      If you want to preserve history, leave it in git but add a `RETIRED` notice
      at the top of any README in that directory.
- [ ] Remove or archive any `agents/` directory that held v1-style role
      definitions the project was using as live governance files.
- [ ] Confirm that no `AGENTS.md`, `.claude/CLAUDE.md`, or equivalent assistant
      loader still imports files from the retired paths.
- [ ] Run `agov validate adoption` after this step and fix any findings that
      reference the retired paths.

### 2. Place project roles under agf/agents/

- [ ] Copy or adapt your project-specific role definitions into `agf/agents/`.
      Use the shipped role templates as a base. Name each file `<role-slug>.yaml`.
- [ ] Update the assistant loader (`.claude/CLAUDE.md` or equivalent) to
      point to the new paths under `agf/`.
- [ ] Run `agov validate agents` and fix any schema findings.

### 3. Move assistant commands and skill sources

- [ ] Identify any assistant-command files (`.claude/skills/`, YAML skill
      definitions, Codex command files) that reference v1 paths.
- [ ] Move or repoint them to `agf/` equivalents. If the commands were
      AGF-provided skills from the v1 distribution, replace them with the
      equivalents from the v2 distribution archive.
- [ ] Verify that no skill or command file hard-codes a local tool path for
      `mix agov.*`, Python validators, or the v1 session-resume flow.

### 4. Update every instruction surface for cold start and tooling

The most common split-brain source after migration.

- [ ] Search all of: `AGENTS.md`, `.claude/CLAUDE.md`, `agf/templates/AGENTS.md`
      (if customized), and any project-specific loader file for references to:
      - `agents-govern/`
      - `mix agov.session.resume` (v1 Elixir form)
      - numeric sequence coordination files (`00001-`, `00002-`)
      - Python validator commands (`python -m agents_govern.*`)
- [ ] Replace each occurrence with the v2 equivalent:
      - `agf/` for the directory reference
      - `agov session resume` for session startup (Rust binary)
      - readable-ID coordination files generated by `agov coord brief --id-format readable`
      - `agov validate <target>` for validation
- [ ] Test the new layout: open a fresh session (or clear context), then verify
      that the first action the session description calls for is `agov session resume`
      pointing to the correct `agf/` path. If a human is doing the migration
      without an AI session, verify the documentation is correct by reading it
      fresh, as if for the first time.

### 5. Replace coordination numbering instructions

- [ ] Remove any instruction that says to increment a sequence counter or use
      zero-padded numeric filenames for new coordination entries.
- [ ] Add or verify that the loader says new coordination entries use
      `agov coord brief --id-format readable` to generate the filename and ID.
- [ ] Historical sequence-numbered files remain as immutable history. Do not
      rename or delete them.

### 6. Update tooling references for colleagues

- [ ] Update any onboarding document, README section, or wiki page that tells
      people how to install the tooling. The v2 Rust `agov` binary is published
      on the [AGF releases page](https://gitlab.com/janipaijanen/agents-govern-framework/-/releases).
      Remove references to installing from source via Elixir/Mix.
- [ ] If CI jobs run validation, update them to call `agov validate <target>`
      instead of v1 Python or Elixir commands.

### 7. Validate the full layout

Run each validator in order. Fix findings before continuing to the next step.

```
agov validate adoption
agov validate agents
agov validate learnings
agov validate infosec
```

If `agov` is not yet installed, download it from the releases page first.
Record which checks were manual in the migration MR description.

### 8. Validate new coordination entries

After the migration is complete, file a coordination note and validate it:

```
agov coord validate docs/coordination/<your-new-entry>.md
```

The new entry should use a readable ID. If it validates cleanly, the tooling
chain is working end-to-end.

### 9. Scan active docs for v1 references

- [ ] Search the full repository for `agents-govern/`, `mix agov`, and any
      numeric coordination sequence patterns (e.g. `\b000[0-9]{2}-`).
- [ ] Any occurrence in a human-readable doc, template, or rule is a remaining
      split-brain surface. Update or annotate each one.
- [ ] Update the `agf/docs/` site pages if any describe v1 paths in the context
      of your local setup.

### 10. Review adopter learning records

A learning record that passes YAML validation may still contain stale content.
After each learning record passes `agov validate learnings`, do a second pass
through each record under these lenses:

- **infosec-sentinel:** does the record contain workstation-local paths,
  private project identifiers, customer names, or details that should stay
  inside your repository?
- **contribution-auditor:** does the record use the framework codename where it
  should, and avoid naming internal identifiers that would be visible upstream?
- **fact-checker:** does the record cite the current framework version, current
  role names, and current tooling commands? A record written during v1 may say
  `agents-govern/`, `mix agov.*`, or `L001` sequential IDs that imply v1
  context.

Update each stale field before the migration MR merges. The learning record
file is adopter-owned; edit it freely.

---

## After the checklist

Once all items are checked:

1. Run the full CI suite if you have one.
2. Test the new layout from scratch: review the loader file as if reading it
   for the first time, or open a fresh AI session and verify it finds the
   right cold-start instructions and current AGF version.
3. File the migration MR with the checklist above as the review body.
4. Gate 2 review: the reviewer should verify at least steps 4, 7, and 10.
5. Write a local learning record for the migration. Evidence that the checklist
   helped (or that it missed something) goes upstream as an issue so the
   checklist can improve.
